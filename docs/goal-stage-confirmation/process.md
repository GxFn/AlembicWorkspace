# 需求目标与分阶段确认流程

状态：长期流程规范
维护窗口：AlembicWorkspace

本流程规定：用户发布较大任务目标后，总控窗口必须先在 `docs/requirement-designs/<需求名>/` 保存原始计划书，并与用户商量确认原始计划书。只有原始计划书确认后，才能按需求调研真实代码并创建需求设计文档；对跨仓库、运行时、项目控制、发布链路、模块边界、删除清理等复杂任务，还必须补充深度代码实现依赖调研；然后确认“本次任务的最终目标与分阶段”，最后才派发任何执行窗口。长期产品路线只能作为背景，不能替代本次任务目标确认。

本流程只处理明确的完整功能模块。需求不明确时，只能进入原始计划书和需求设计文档的“待确认问题”，不能进入执行派发。不得把不明确需求包装成抽象接口、空 adapter、空 provider、无调用方 glue code 或只连线不形成用户可用能力的任务。

## 触发条件

满足任一条件时，必须先创建 `docs/requirement-designs/<需求名>/` 下的原始计划书，并等待用户确认。原始计划书确认后，才能创建需求设计文档和任务级目标阶段确认文档：

- 用户提出新的跨仓库目标、路线调整、功能删除、模块拆分、发布链路、架构边界或多窗口执行请求。
- 现有任务中途新增关键约束，可能改变执行顺序、仓库职责、删除边界或验证范围。
- 总控发现当前执行计划缺少最终完成定义、阶段顺序或 producer / consumer 依赖判断。

小范围单仓库修复、纯验收总结、只改总控文档错字时，可以不创建新确认文档，但仍要遵守窗口覆盖和不空转规则。

## 标准流程

1. 暂停派发：把当前总控入口或当前计划改为 `暂停` / `等待调研`，发送名单必须为 `无`。
2. 建立需求目录：在 `docs/requirement-designs/<需求名>/` 新建 `README.md` 和 `original-plan-YYYY-MM-DD.md`；不要提前创建需求设计文档和目标阶段确认文档。
3. 保存原始计划书：把用户原始需求、原始计划口径、约束和后续补充写入 `original-plan-YYYY-MM-DD.md`，不夹带实现判断。
4. 原始计划书确认：在 `docs/workspace/` 新建或更新原始计划书确认入口，发送名单必须为 `无`；最终回复只请用户确认原始计划书或指出调整。
5. 用户确认原始计划书：只有用户确认后，才能进入代码调研和目标阶段设计。
6. 功能分析：总控先分析需求的功能本质、用户场景、完整能力边界、输入输出、状态变化和完成定义，不能直接把需求翻译成任务表。
7. 本地代码调研：读取当前任务相关的 workspace 文档、目标仓库 `AGENTS.md`、真实代码入口、调用方、测试和发布脚本，确认当前系统真实能力和连通性。
8. 外部调研判断：根据需求类型判断是否需要联网查找官方文档、成熟项目或业界最佳实践；若需要，优先使用官方文档、主流项目源码 / 文档或权威资料，并在需求设计文档中记录来源；若不需要，也要记录不联网的理由。
9. 建立需求设计文档：按用户需求、本地代码事实和必要外部调研形成需求设计文档；模板见 [../requirement-designs/requirement-design-template.md](../requirement-designs/requirement-design-template.md)。
10. 明确功能闭环：需求设计文档必须写清用户场景、完整功能闭环、输入输出、状态 / 数据变化、生产方、消费方、验证命令和完成标准；缺任一关键项时，状态保持等待确认。
11. 标记阶段候选：需求设计文档可以写“后续拆分候选方向”，但这不是执行派发依据；不能把候选阶段标成 `待启动`。
12. 深度代码实现依赖调研：对复杂任务，在需求目录下创建 `code-implementation-dependency-research-YYYY-MM-DD.md` 或等价附件，记录真实代码入口、生命周期、共享状态、持久化位置、producer / consumer、不能切换或不能删除的硬边界，以及是否需要外部资料。
13. 建立目标阶段确认文档：基于需求设计文档和深度代码证据，按 [template.md](template.md) 新建任务级确认文档。
14. 写清本次任务：包含用户原始目标、原始计划书链接、需求设计文档链接、代码实现依赖调研链接、总控理解、最终完成定义、非目标、影响窗口、依赖链、阶段计划、验证策略和确认问题。
15. 更新索引：把 `docs/workspace/index.md` 第一行切到当前确认入口，并同步 `workspace-current-status.md`；同时在当前入口挂载需求目录、原始计划书、需求设计和代码实现依赖调研。
16. 等待用户确认目标阶段：在用户确认前，不输出可复制执行提示词，不把任何执行窗口标成 `待启动`。
17. 确认后创建 wave 执行计划：用户确认后，新建或激活 `docs/workspace/<topic>-wave-N-...-plan-YYYY-MM-DD.md`，把 `docs/workspace/index.md` 第一行切到该 wave 执行计划，并同步 `workspace-current-status.md`。
18. 确认后派发：只把当前无上游阻塞、发送后能实际推进的窗口标为 `待启动` 或 `执行中`，并输出可复制提示词。
19. 波次推进：每波完成后，先验收当前 wave 回填，再决定是否进入下一波、统一验收或回到目标阶段调整。
20. 功能完整性验收：验收时必须检查真实入口、真实数据来源、状态 / 数据变化、真实消费方、失败 / 边界路径和用户可执行验证；如果只是最小接口连接、静态 mock、空壳 API、未被消费的 contract 或只改类型导出，不能标为已完成。
21. 最小实现补齐：如果发现最小实现，必须新开或插入一轮“非最小完整实现补齐” wave，明确缺失功能闭环、执行窗口、验证命令和完成定义；补齐前不得继续派发依赖该能力的下游窗口。
22. 范围变化：如果用户新增目标或总控发现阶段顺序错误，回到第 1 步重新调研 / 确认，不在旧派发口径上继续加任务。

## 文档要求

- 任务级确认文档允许带日期，因为它记录一次具体用户目标。
- 原始计划书和需求设计文档必须保存在 `docs/requirement-designs/<需求名>/`，允许带日期，因为它们记录一次具体需求调研。
- 长期模板和流程规范不带日期，作为可复用规则保留。
- 原始计划书必须有用户确认记录；没有确认记录时，不应创建或激活需求设计文档、任务级目标阶段确认或派发文档。
- 任务级确认文档必须链接对应已确认的原始计划书、需求设计文档，以及复杂任务所需的代码实现依赖调研；缺任一项，不应进入确认或派发。
- 需求设计文档和确认文档必须把任务定义为完整功能模块；如果只剩抽象连接、占位接口、空实现或无真实消费方的代码连接，不应进入派发。
- 确认文档必须有 `## 窗口分派`、`## 可复制提示词` 和 `## 回填区`，以便 workspace 脚本校验。
- 确认前的 `发送给` 必须是 `无`；不要把候选执行窗口写成可发送名单。
- 如果已有 wave 文档可复用，确认文档仍然必须说明它只是“确认后可启用的候选计划”。
- 用户确认后，当前计划入口应切到具体 wave 执行计划；目标阶段确认文档保留确认记录和阶段路线，不承载所有执行回填。

## 派发约束

- 最终覆盖窗口可以包含未来会参与的仓库；当前可派发窗口只能包含没有上游阻塞的仓库。
- 状态为 `观察中`、`无任务`、上游未完成的 `阻塞` 或目标未确认的 `暂停`，都不发送提示词。
- 总控必须人工核对依赖链；`check-dispatch-coverage` 只检查覆盖和状态，不判断阶段顺序是否合理。
- 其它窗口不得自行提交 AlembicWorkspace 文档；总控确认后统一提交 workspace 仓库。
- 新建 / 激活确认文档或 wave 执行计划后，应运行 `node scripts/verify-workspace-docs.mjs --all-workspace`、`node scripts/check-dispatch-coverage.mjs` 和 `git diff --check`。

## 验收完整性规则

- 验收不能只看 build / lint / test 是否通过，也不能只看接口是否接通。
- 必须确认功能是否能被真实用户或真实下游窗口实际使用。
- 必须检查输入输出、状态 / 数据变化、持久化位置、真实数据来源、真实调用链、真实消费方、错误 / 边界路径和回滚 / 保留策略。
- 如果实现只提供最小连接、空壳 API、静态数据、mock 路由、未被消费的 contract、无入口 service、无 UI / CLI / API 消费路径，或无法说明用户如何真实使用，必须标为返工 / 待补齐，而不是已完成。
- 最小实现补齐必须形成单独 wave 或当前 wave 的返工任务，写清缺失项、补齐目标、禁止继续下游的依赖原因和验收命令。

## 输出给用户

原始计划书确认前，总控最终回复只应说明：

- 已创建或更新哪份原始计划书。
- 当前派发已暂停，发送名单为无。
- 请用户确认原始计划书，或指出要调整的原始目标和约束。

目标阶段确认前，总控最终回复只应说明：

- 已创建或更新哪份原始计划书和需求设计文档。
- 已创建哪份任务级确认文档。
- 当前派发已暂停，发送名单为无。
- 请用户确认目标和阶段，或指出要调整的范围。

确认后，才输出可复制执行提示词。
