# Swift 泛型的实现

- **Original title**: Implementing Swift Generics
- **原文链接**: [LLVM Developers' Meeting 2017](https://llvm.org/devmtg/2017-10/)
- **作者/机构**: Douglas Gregor、Slava Pestov、John McCall / Apple
- **年份**: 2017
- **材料类型**: LLVM 开发者大会编译器演讲与幻灯片
- **文档性质**: 忠实中文精读，不是原文全文翻译

## 文章要解决的问题

泛型编译常见两端：一种把值统一装箱，以固定表示换取共享代码；另一种为每组具体类型生成专用机器码。Swift 既要高性能，又要支持独立编译、值类型和未知布局。原文解释它如何通过运行时元数据与见证信息生成可共享的泛型实现，并在条件允许时再做特化。

## 原文论证主线

类型检查阶段先把源码约束规范化为泛型签名。进入代码生成后，一个未特化泛型函数不能预先知道 `T` 的大小、对齐、复制或销毁方式，于是调用方传入类型元数据；编译代码通过 value witness 提供的操作处理未知布局值。若 `T: P`，还要提供描述该具体一致性的 protocol witness，使函数可以调用协议 requirement。隐藏参数共同构成类似 dictionary passing 的实现模型。

## 关键机制与结论

运行时元数据让同一份泛型机器码处理多种布局，而无需把所有值转换成统一对象。value witness 负责布局相关的初始化、复制、移动和销毁；protocol witness 连接协议 requirement 与符合类型的实现。编译器看到具体实参且具备函数体可见性时，可以生成特化版本，常量化元数据和见证、展开布局并进一步内联；但未特化路径仍是 Swift 独立编译模型的重要组成。

## 准确性与版本边界

这是 ABI 稳定前的 2017 年实现讲解，编译器数据结构、调用约定细节和优化 pass 已继续演化。元数据、value witness、protocol conformance 与特化之间的总体关系仍是理解现代 Swift 的基础。不能把它简化为“Swift 泛型一定像 C++ 模板一样复制代码”，也不能反向写成“所有泛型调用都必须在运行时查表”；专用化、内联和去虚化会改变最终机器码。

## 在知识体系中的位置

该演讲连接了源码泛型与 ABI/运行时。它适合在掌握 `some`、`any` 和关联类型之后阅读，并与《Compiling Swift Generics》分工：本篇强调从类型检查到 LLVM IR、元数据与调用约定，后者更系统地建立编译器内部的类型、替换、一致性和 requirement machine 模型。
