# 现代 Swift API 设计

- **Original title**: Modern Swift API Design
- **原文链接**: [Apple Developer](https://developer.apple.com/videos/play/wwdc2019/415/)
- **作者/机构**: Ben Cohen、Douglas Gregor / Apple
- **年份**: 2019
- **材料类型**: WWDC API 设计演讲与文字稿
- **文档性质**: 忠实中文精读，不是原文全文翻译

## 文章要解决的问题

API 的使用者面对的是行为，而不是作者选了 struct 还是 class。原文讨论如何让 Swift API 在调用点清晰、难以误用，并使类型的复制、共享和身份符合领域模型，而不是由偶然的实现细节决定。

## 原文论证主线

演讲从命名和“调用点清晰”进入值与引用的选择。具有独立副本含义的材料、配置和属性适合值语义；代表引擎中唯一实体、共享资源或稳定身份的对象适合引用语义。随后它展示一个 struct 包含 class 属性时的风险：复制外层值只会复制引用，如果内部对象可变，两个外层副本就不再真正独立。解决方案包括不可变共享、隐藏引用、复制隔离或 COW。

## 关键机制与结论

“优先考虑 struct”是起点，不是终点。判断标准应是对象是否有独立于属性值的身份、是否需要共享观察同一状态、生命周期是否管理资源。协议用于描述语义能力，泛型保留具体类型关系；存在类型适合需要异质存储或运行时替换的边界。文章还借 key-path dynamic member lookup 和 property wrapper 说明：语言功能应把重复机制封装起来，但公开 API 仍需让数据流、可变性和错误路径容易理解。

## 准确性与版本边界

材料基于 Swift 5.1，尚未覆盖宏、现代存在类型拼写、所有权修饰和 Swift 6 并发隔离。属性包装器也不是隐藏任意副作用的许可。Swift-only 模块通常不需要 Objective-C 式前缀，但同时暴露给 Objective-C 的 API 仍受互操作命名和运行时约束。COW 是可选实现策略，不是声明 struct 后自动获得的语言行为。

## 在知识体系中的位置

这篇文章把值语义、泛型和库设计从“语言知识”提升到“接口判断”。它适合用作面试文档的设计原则层：先明确领域语义和调用者预期，再选择类型、抽象与优化手段；之后可接《Library Evolution in Swift》理解公开二进制 API 还需要承担哪些长期承诺。
