# 探索 Swift 性能

- **Original title**: Explore Swift performance
- **原文链接**: [Apple Developer](https://developer.apple.com/videos/play/wwdc2024/10217/)
- **作者/机构**: John McCall / Apple Swift 团队
- **年份**: 2024
- **材料类型**: WWDC 编译器与性能演讲、文字稿
- **文档性质**: 忠实中文精读，不是原文全文翻译

## 文章要解决的问题

Swift 的抽象不会简单映射成一条固定成本规则。闭包、异步函数、动态尺寸值和泛型都可能涉及调用、存储、复制与分配，而优化器又会消除其中一部分。原文要培养的是判断成本来源的直觉，并说明性能调查为何必须从用户可见问题和测量开始。

## 原文论证主线

演讲先把低层成本归纳为函数调用、数据表示、内存分配以及不必要的复制与销毁。随后分别观察函数能否直接调用或内联，值的大小与对齐怎样影响传递，堆分配为何比内联存储更重，以及值复制是否只复制少量字段、触发引用计数或执行更复杂操作。最后把这些原则应用到动态尺寸类型、async frame、闭包捕获和泛型。

## 关键机制与结论

局部变量不是天然等于栈存储：逃逸闭包、跨 `await` 存活的状态或动态生命周期会改变存储位置，优化器也可能把分配消除。泛型共享实现可以借助元数据处理未知布局，具体类型可见时又可能特化。函数值需要携带代码入口和上下文，是否分配取决于捕获和逃逸。性能工作的第一优先级仍是算法和宏观测量；低层模型用于解释已定位热点，而不是提前改写全部代码。

## 准确性与版本边界

文章接近 Swift 6 发布时的实现，是比 2016 演讲更现代的基线，但它仍描述实现策略和优化机会，而非每个版本都必须产生的机器码。`struct` 不保证栈分配，`any` 不保证堆分配，泛型不保证特化，动态派发也可能被去虚化。具体结论必须在目标编译器、优化级别、平台和真实输入下用 Instruments 或可重复基准验证。

## 在知识体系中的位置

它是性能主干的现代总览。建议先读它建立四类成本，再回看《Understanding Swift Performance》补充协议存在容器的经典模型，最后用《Improve memory usage and performance with Swift》了解 Swift 6.2 的低层内存工具。
