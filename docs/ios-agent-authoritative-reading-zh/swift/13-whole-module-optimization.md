全模块优化是 Swift 编译器的一种优化模式。
全模块优化带来的性能收益在很大程度上取决于具体项目，但提升幅度可能达到两倍，甚至五倍。

可以通过 `-whole-module-optimization`（或 `-wmo`）编译器标志启用全模块优化；在 Xcode 8 中，新建项目默认开启该模式。
此外，Swift Package Manager 在构建发布版本时也会采用全模块优化。

那么，它究竟是怎么回事？我们先来看一下不使用全模块优化时编译器如何工作。

### 模块以及如何编译模块

模块是一组 Swift 文件。每个模块最终会编译成一个独立的分发单元——框架或可执行文件。在单文件编译模式下（不使用 `-wmo`），Swift 编译器会分别针对模块中的每个文件运行。实际上，这些工作都发生在幕后。用户不需要手动执行；编译器驱动程序或 Xcode 构建系统会自动完成。

![单文件编译](https://www.swift.org/assets/images/wmo-blog/single-file.png)

读取并解析源文件（以及执行类型检查等其他工作）之后，编译器会优化 Swift 代码、生成机器码并写出目标文件。最后，链接器将所有目标文件合并，生成动态链接库或可执行文件。

在单文件编译模式下，编译器的优化范围仅限于单个文件。因此，函数内联、泛型特化等跨函数优化，只能作用于在同一文件中调用并定义的函数。

来看一个例子。假设模块中有一个名为 utils.swift 的文件，其中包含泛型实用数据结构 `Container<T>` 及其 `getElement` 方法；该方法会在整个模块中被调用，例如在 main.swift 中调用。

main.swift：

~~~swift
func add (c1: Container<Int>, c2: Container<Int>) -> Int {
  return c1.getElement() + c2.getElement()
}
~~~

utils.swift：

~~~swift
struct Container<T> {
  var element: T

  func getElement() -> T {
    return element
  }
}
~~~

编译器优化 main.swift 时，并不知道 `getElement` 是如何实现的，只知道这个方法存在。因此，编译器会生成一次对 `getElement` 的调用。另一方面，编译器优化 utils.swift 时，并不知道这个函数会针对哪些具体类型被调用。因此，它只能生成该函数的泛型版本；与针对具体类型特化的代码相比，这个版本要慢得多。

就连 `getElement` 中那条简单的 return 语句，也需要查询类型的元数据，才能确定如何复制元素。该元素可能只是一个简单的 `Int`，也可能是更大的类型，甚至涉及一些引用计数操作。编译器并不知道具体情况。

### 全模块优化

采用全模块优化后，编译器可以做得好得多。使用 `-wmo` 选项编译时，编译器会把模块中的所有文件作为一个整体进行优化。

![全模块编译](https://www.swift.org/assets/images/wmo-blog/wmo.png)

这带来两项重要优势。第一，编译器能够看到模块中所有函数的实现，因此可以执行函数内联和函数特化等优化。
函数特化是指编译器创建一个针对特定调用上下文优化过的新函数版本。例如，编译器可以针对具体类型来特化泛型函数。

在我们的例子中，编译器会生成一个针对具体类型 `Int` 特化的泛型 `Container` 版本。

~~~swift
struct Container {
  var element: Int

  func getElement() -> Int {
    return element
  }
}
~~~

然后，编译器可以把特化后的 `getElement` 函数内联到 `add` 函数中。

~~~swift
func add (c1: Container<Int>, c2: Container<Int>) -> Int {
  return c1.element + c2.element
}
~~~

这段代码最终只会编译成少量机器指令。与单文件编译生成的代码相比，差别非常大：后者还需要对泛型 `getElement` 函数进行两次调用。

跨文件的函数特化和内联，只是编译器在全模块优化模式下能够执行的优化示例。即使编译器决定不内联某个函数，能够看到该函数的实现也会大有帮助。
例如，编译器可以分析该函数在引用计数操作方面的行为。借助这些信息，编译器能够移除函数调用前后多余的引用计数操作。

全模块优化的第二项重要优势是，编译器可以分析非公开函数的全部使用方式。非公开函数只能在模块内部使用，因此编译器能够确定自己看到了对这些函数的所有引用。编译器可以利用这些信息做什么呢？

一项很基础的优化，是消除所谓的“死”函数和方法，也就是从未被调用或以其他方式使用的函数与方法。借助全模块优化，编译器能够判断某个非公开函数或方法是否完全未被使用；如果确实如此，就可以将它移除。
可是，程序员为什么要编写一个完全不会被使用的函数呢？其实，这并不是死函数消除最重要的使用场景。很多时候，函数会因为其他优化的副作用而变成死代码。

假设 `add` 函数是唯一调用 `Container.getElement` 的地方。内联 `getElement` 之后，这个函数就不再被使用，因此可以将其移除。即使编译器决定不内联 `getElement`，也仍然可以移除 `getElement` 原来的泛型版本，因为 `add` 函数只会调用特化版本。

### 编译时间

在单文件编译模式下，编译器驱动程序会在独立进程中启动每个文件的编译，这些工作可以并行进行。此外，从上次编译以来没有修改过的文件，无须重新编译（前提是它的所有依赖项也都没有修改）。这称为增量编译。
所有这些机制都能显著缩短编译时间，尤其是在只做了少量修改时。
那么，在全模块编译模式下，这些机制如何运作呢？
我们更详细地看一下编译器在全模块优化模式下的工作方式。

![全模块编译的详细过程](https://www.swift.org/assets/images/wmo-blog/wmo-detail.png)

编译器内部会依次经历多个阶段：解析器、类型检查、SIL 优化以及 LLVM 后端。

在大多数情况下，解析和类型检查都非常快；我们预计，它们在后续 Swift 版本中还会变得更快。
SIL 优化器（SIL 是“Swift Intermediate Language”，即“Swift 中间语言”的缩写）会执行所有重要的 Swift 特有优化，例如泛型特化、函数内联等。这个编译阶段通常约占总编译时间的三分之一。
大部分编译时间消耗在 LLVM 后端上；它负责运行更底层的优化并生成代码。

SIL 优化器完成全模块优化后，模块会再次拆分成多个部分。LLVM 后端使用多个线程处理这些拆分后的部分。如果某一部分自上次构建以来没有发生变化，LLVM 后端还会避免重复处理它。
因此，即使启用了全模块优化，编译器仍然能够以并行（多线程）和增量方式完成编译工作中的很大一部分。

### 结论

借助全模块优化，你无须担心如何把 Swift 代码分散到模块内的不同文件中，也能获得最高性能。
如果上文所述的优化恰好能作用于关键代码区域，与单文件编译相比，性能最高可提升至五倍。
而且，与典型的单体式全程序优化方案相比，全模块优化能以好得多的编译时间换来这种高性能。
