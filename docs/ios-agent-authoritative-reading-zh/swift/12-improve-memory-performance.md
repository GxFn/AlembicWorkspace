# 改善 Swift 的内存使用与性能

- **Original title**: Improve memory usage and performance with Swift
- **原文链接**: [Apple Developer](https://developer.apple.com/videos/play/wwdc2025/312/)
- **作者/机构**: Nate Cook / Apple Swift 标准库团队
- **年份**: 2025
- **材料类型**: WWDC 性能演讲、示例代码与文字稿
- **文档性质**: 忠实中文精读，不是原文全文翻译

## 文章要解决的问题

当解析器或数据处理代码出现速度、峰值内存和引用计数压力时，开发者容易直接进入指针微优化。原文以实际解析工作负载说明更可靠的顺序：先改变算法和数据流，再减少分配与复制，最后才使用 Swift 6.2 的低层安全抽象消除剩余开销。

## 原文论证主线

演讲先从算法层减少重复工作，然后追踪临时集合、缓冲区增长和中间对象造成的分配。接着讨论独占访问检查、栈与堆、ARC retain/release，说明即使类型安全，表示方式仍会在热点中产生额外操作。最后引入固定容量、内联存储的 `InlineArray`，以及受生命周期约束、不可逃逸的连续内存视图 `Span`，并以值泛型和非逃逸类型解释其静态安全基础。

## 关键机制与结论

`InlineArray` 把元素直接放进值的表示，适合编译期已知且较小的固定容量；它可能避免单独缓冲区分配，但整体值放在哪里仍由容器和优化决定。`Span` 借用既有连续内存，不拥有缓冲区，通过不可逃逸约束防止视图活得比来源更久。两者的价值是让编译器验证生命周期和边界，而不是回退到无法证明安全的裸指针。优化前仍应建立指标，验证内存下降没有换来算法退化或复制增长。

## 准确性与版本边界

材料针对 Swift 6.2，新类型、语法和平台可用性必须按项目部署目标核对。演示得到的 retain/release 消除、栈上布局或速度提升是特定源码与优化器的结果，不是采用某个类型后的语言保证。固定内联容量也会增大外层值，容量大或频繁复制时未必更优；`Span` 是借用视图，不应被包装成长期拥有型存储。

## 在知识体系中的位置

它位于性能与所有权的交叉点：前半部分是任何 Swift 版本都适用的测量和表示方法，后半部分展示所有权、非逃逸和值泛型如何服务安全的系统编程。适合在现代性能总览和非复制类型之后阅读。
