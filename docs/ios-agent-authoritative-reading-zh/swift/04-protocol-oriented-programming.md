# Swift 中的协议导向编程

- **Original title**: Protocol-Oriented Programming in Swift
- **原文链接**: [Apple Developer](https://developer.apple.com/videos/play/wwdc2015/408/)
- **作者/机构**: Dave Abrahams / Apple Swift 标准库团队
- **年份**: 2015
- **材料类型**: WWDC 语言设计演讲与文字稿
- **文档性质**: 忠实中文精读，不是原文全文翻译

## 文章要解决的问题

传统类继承能封装数据、复用代码并提供动态定制，但也带来隐式共享、单继承约束、基类状态负担和类型关系丢失。原文不是要废除面向对象，而是证明 Swift 的协议、泛型和值语义能够在许多场景中形成更精确、更可组合的抽象。

## 原文论证主线

演讲从类的三类代价展开：共享可变对象破坏局部推理；继承把存储、初始化和可覆盖契约绑在一起；用基类表达比较等对称关系时，参数类型容易退化为基类并迫使向下转换。协议的 `Self` requirement 能保存“操作双方必须是同一种具体类型”的关系，泛型算法再以同质集合使用它。随后通过 Renderer、Drawable 和不同图形类型展示协议、结构体、适配器与测试替身如何组合。

## 关键机制与结论

协议定义能力和语义契约，扩展可复用默认算法，约束扩展可在满足附加关系时开放能力。声明为 requirement 的操作是符合类型的自定义点；扩展中额外的方法只是基于静态类型可用的共享实现。值类型组合值类型，有助于获得独立修改和可预测状态；协议则让不相关的具体类型参与同一算法。原文的核心并非“多写协议”，而是让抽象保存真正的类型关系，并把共享实现与共享存储分开。

## 准确性与版本边界

这是 Swift 2 时代演讲。当时“带 `Self` 或关联类型的协议不能作为类型”的表述已被现代 `any`、隐式打开存在类型和主关联类型显著改写。存在值仍会隐藏部分类型关系，泛型也仍更适合表达同一具体类型。演讲中的“不要从 class 开始”是设计启发，不是语言规则；需要稳定身份、共享可变资源、Objective-C 互操作或框架继承时，class 仍然合理。

## 在知识体系中的位置

它是理解 Swift 标准库设计、协议扩展、静态多态与值语义的历史主干。阅读后应接续现代泛型两场 WWDC22 演讲，以更新 `some`/`any` 语法，再用派发文章补足 requirement 与扩展方法的行为差异。
