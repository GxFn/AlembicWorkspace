# 设计 Swift 协议接口

- **Original title**: Design protocol interfaces in Swift
- **原文链接**: [Apple Developer](https://developer.apple.com/videos/play/wwdc2022/110353/)
- **作者/机构**: Slava Pestov / Apple Swift 编译器团队
- **年份**: 2022
- **材料类型**: WWDC 语言设计演讲与文字稿
- **文档性质**: 忠实中文精读，不是原文全文翻译

## 文章要解决的问题

协议一旦包含关联类型或 `Self` 关系，接口设计就不仅是列出若干方法。调用方可能需要隐藏实现、保存类型关系，或者让容器容纳多种符合者。原文讨论如何在存在类型、opaque type 和泛型约束之间选择，使抽象既可用又不丢掉完成算法所需的信息。

## 原文论证主线

第一部分考察 `any P`。存在值隐藏了内部具体类型，调用 requirement 后，结果中依赖 `Self` 的部分可能继续被擦除为可公开表示；若操作要求两个值拥有同一隐藏类型，则调用方通常不能仅凭两个独立存在值证明这个关系。第二部分转向 `some P`：接口隐藏实现选定的具体类型，但同一声明产生的隐藏类型具有稳定身份，因此关联类型关系仍能传播。最后通过 same-type requirement，把多个协议或关联类型之间必须相等的关系写进约束。

## 关键机制与结论

`any` 解决的是值级别的类型擦除与异质性，`some` 解决的是实现隐藏但保留类型身份，显式泛型解决的是由调用方提供类型并建立参数间关系。协议设计不应只问“有哪些方法”，还要问调用算法必须证明哪些等式、谁选择具体类型、值是否需要在一次赋值后换成另一种符合者。无法表达必要关系时，强制转换只是丢失建模信息后的补丁。

## 准确性与版本边界

演讲基于 Swift 5.7。隐式打开存在类型在 Swift 6 language mode 中又扩展了部分传参能力，主关联类型、参数包和非复制泛型也继续演进；但它们没有消除 `some` 与 `any` 的语义差异。存在值可能使用内联缓冲、间接存储和见证信息，但具体分配与派发可被优化，不能把“使用 `any`”直接等同于“必然堆分配且一定慢”。

## 在知识体系中的位置

它是《Embrace Swift generics》的直接进阶，适合作为协议章节的现代主体。读完后再看 opaque result type、existential `any` 等 Swift Evolution 提案，可以理解语法背后的取舍；进入编译器材料后，则可把“隐藏类型身份”和 substitution、conformance 等内部模型对应起来。
