## 引言

为 Swift 加入“所有权”是一项重大特性，可以为程序员带来许多好处。本文既是一份关于所有权的“宣言”，也是一份“元提案”：它阐述这项工作的基本目标，描述实现这些目标的一般方法，并提出多项具体修改和特性；其中每一项都需要在规模更小、目标更集中的提案中分别讨论。本文旨在提供一个框架，帮助理解这些修改各自作出的贡献。

### 问题陈述

写时复制值类型在 Swift 中得到广泛使用，总体而言是成功的。不过，它确实也存在一些缺点：

* 引用计数和唯一性检查的确会产生一定开销。

* 在大多数情况下，引用计数可以提供确定性的性能，但这种性能仍然可能难以分析和预测。

* 值随时可以被复制并由此“逃逸”，这迫使底层缓冲区通常必须在堆上分配。栈分配的效率要高得多，但它要求具备某种能力，能够阻止——或者至少识别——让值逃逸的尝试。

某些底层编程任务要求更严格的性能保证。这些保证关注的往往不是绝对性能，而是*可预测的*性能。例如，对现代处理器而言，即使每个采样点都有显著开销，跟上音频流也并不困难；但任何意外卡顿都会立即被用户察觉。

另一项常见的编程任务，是在既有代码没有达到某个性能目标时对其进行优化。这往往意味着找出执行时间或内存使用中的“热点”，再设法修复。若这些热点源于隐式复制，Swift 目前用于解决问题的工具相当有限；例如，程序员可以退回到使用不安全指针，但这会失去库集合类型在安全性和表达能力方面的许多优势。

我们认为，可以通过一组选择加入的特性来解决这些问题；我们把这些特性统称为*所有权*。

### 什么是所有权？

*所有权*是指某段代码负有最终使某个值被销毁的责任。*所有权系统*则是管理和转移所有权的一组规则或约定。

任何具有销毁概念的语言，都具有所有权概念。在 C 和非 ARC Objective-C 等语言中，所有权由程序员显式管理。在 C++（部分情形）等语言中，所有权由语言管理。即使是采用隐式内存管理的语言，其库中也仍然存在所有权概念，因为除了内存以外，程序还有其他资源；理解哪段代码负责释放这些资源非常重要。

Swift 已经有一套所有权系统，但它藏在“幕后”：它是一项实现细节，程序员几乎无法影响。我们在这里提出的方案很容易概括：

- 我们应该向所有权系统加入一条核心规则，称为独占法则（Law of Exclusivity）；它要求实现阻止以彼此冲突的方式同时访问变量。（例如，把同一个变量作为 `inout` 参数传给两个不同的函数。）这不是一项选择加入的修改，但我们相信绝大多数程序不会因此受到不利影响。

- 我们应该添加一些特性，让程序员能够更大程度地控制所有权系统，主要方式是允许“共享”值传播。这是一项选择加入的修改；它主要由标注和语言特性构成，程序员完全可以不用。

- 我们应该添加一些特性，让程序员可以表达具有唯一所有权的类型，也就是不能被隐式复制的类型。这是一项面向资深程序员的选择加入特性，适合希望拥有这种控制能力的人；我们不打算让普通 Swift 编程必须处理此类类型。

这三根支柱共同把所有权系统从实现细节提升为语言中更加可见的一部分。由于下文将解释的原因，它们在某种程度上也不可分割，当然各自的优先级可以不同。因此，我们会把它们作为一项统一的特性，统称为“所有权”。

### 再详细一点

Swift 当前所有权系统的根本问题是复制，而所有权的三根支柱都围绕避免复制展开。

一个值可能会在程序中的许多不同位置使用。实现必须确保该值的某个副本能够存活，并可供每个位置使用。只要类型可复制，就总能通过创建更多值副本来满足这一点。然而，大多数使用方式实际上并不要求拥有自己的副本。有些确实需要：如果变量不拥有自己的当前值，它就只能存储那些已知由别处拥有的值，这通常并没有多大用处。但是，从类实例中读取一个值这样的简单操作，只要求该实例继续有效，并不要求执行读取的代码本身拥有对它的引用。有时这种区别很明显，但往往无法判断。例如，编译器通常不知道任意函数会如何使用参数，只能退回到一条默认规则，决定是否传递值的所有权。当默认规则不正确时，程序最终会在运行时制造额外副本。因此，我们能做的一件简单的事，就是允许程序在某些位置更明确地说明自己是否需要所有权。

这与支持不可复制类型的诉求紧密契合。大多数资源只能有一个销毁点：一块内存只能释放一次，一个文件只能关闭一次，一把锁只能释放一次，依此类推。因此，对这类资源的拥有型引用天然具有唯一性，也就不可复制。当然，我们可以人为地允许共享所有权，例如添加引用计数，并且仅当计数归零时才销毁资源。但这会显著增加操作资源的开销；更糟的是，它还会引入并发和可重入性问题。如果所有权是唯一的，而语言能够强制规定只有拥有资源的代码才能对该资源执行某些操作，那么从构造上讲，同一时刻就只会有一段代码执行这些操作。一旦所有权可以共享，这一性质就消失了。因此，让语言直接支持不可复制类型很有意义，因为它们允许对资源表达效率最优的抽象。不过，要使用这类类型，就必须在函数参数等所有抽象点上正确标注是否转移所有权，因为编译器再也无法通过在幕后添加复制来让代码工作。

若想妥善解决上述任一问题，还需要解决对变量进行非独占访问的问题。如今的 Swift 允许对同一变量进行嵌套访问；例如，可以把一个变量作为两个不同的 `inout` 参数传入，或者向某个方法传递一个回调，而该回调又以某种方式访问该方法调用所针对的同一个变量。这种做法大多不受鼓励，却没有被禁止；编译器和标准库都不得不竭尽全力，确保即使发生这种情况，程序也不会表现得过于糟糕。例如，`Array` 在原地修改元素期间必须保留其缓冲区；否则，如果该修改以某种方式重新赋值数组变量，缓冲区就会在元素仍被修改时释放。同样，编译器通常很难证明内存中的值在函数不同位置上仍然相同，因为它必须假定任何不透明的函数调用都可能重写全部内存；结果就是出于谨慎，它往往不得不插入复制或保留多余的加载。更糟的是，非独占访问会严重限制显式标注的用途。例如，“共享”参数只有在确实保证其整个调用期间都保持有效时才有用；但对于能够被可重入地修改的变量，其当前值要可靠地满足这一点，唯一的办法就是先创建副本再传入。非独占访问还会使某些重要模式变得不可能，例如取走变量的当前值，用它来构建新内容；如果其他代码可以在操作进行到一半时访问该变量，这种做法就是不可靠的。唯一的解决方案是建立一条规则，防止多个上下文同时访问同一个变量。这正是我们通过独占法则所要实现的目标。

这三个目标紧密相连，并会相互加强。独占法则让显式标注默认就能真正优化代码，并支持不可复制类型所必需的编程方式。显式标注在独占法则之下创造更多优化机会，也让不可复制类型能够运作。不可复制类型可以验证这些标注即使对可复制类型也是最优的，并创造更多能够静态满足独占法则的场景。

### 成功标准

如上所述，核心团队预期所有权可以作为 Swift 的一项选择加入式增强功能交付。程序员应该能够在很大程度上忽略所有权，同时不为此付出代价。如果事实证明这一预期无法实现，我们宁愿拒绝所有权，也不会给普通程序施加沉重负担。

独占法则会施加一些新的静态和动态限制。我们认为，这些限制只会影响少量代码，而且只会影响那些执行了我们已经明确记载为结果未指定之操作的代码。这些限制在动态执行时也会损害性能。我们希望，改进后的优化潜力能够“抵偿”这项成本。必要时，我们还会为程序员提供消除这些安全检查的工具。本文稍后会更详细地讨论这些限制。

## 核心定义

### 值

任何关于所有权系统的讨论，都必然处在较低的抽象层级。我们会大量讨论实现层面的主题。在这个语境中，当我们说“值”时，指的是语义上的、用户语言中的某个值的特定实例。

例如，考虑下面的 Swift 代码：

```swift
var x = [1,2,3]
var y = x
```

人们常会说，此时 `x` 和 `y` 拥有相同的值。我们把它称为*语义值*。但在实现层面，由于变量 `x` 和 `y` 可以各自独立修改，`y` 中的值必须是 `x` 中值的一个副本。我们把它称为*值实例*。一个值实例可以在内存中移动而仍然是同一个值实例，但复制总会产生一个新的值实例。本文余下部分在没有限定词地使用“值”时，指的都是这个较低层面的值实例。

复制或销毁一个值实例具体意味着什么，取决于它的类型：

* 有些类型除了复制其字节表示之外，不需要额外工作；我们称之为*平凡类型（trivial）*。例如，`Int` 和 `Float` 是平凡类型，只包含此类值的普通 `struct` 和 `enum` 也是如此。本文有关所有权的大部分论述都不适用于这些类型的值。不过，独占法则仍然适用于它们。

* 对于引用类型，值实例是对某个对象的引用。复制值实例意味着创建一个新引用，从而增加引用计数。销毁值实例意味着销毁一个引用，从而减少引用计数。当然，引用计数减少后可能变为零，进而销毁对象；但必须记住，所有这些关于复制和销毁值的讨论，指的是操作引用计数，而不是复制对象或（必然）销毁对象。

* 对于写时复制类型，值实例包含一个指向缓冲区的引用，而该引用随后基本上像引用类型一样工作。同样，必须记住，复制值并不意味着把缓冲区的内容复制到一个新缓冲区。

每一种类型都有类似的规则。

### 内存

一般来说，一个值可以用两种方式之一被拥有：它可以“在途”，即作为某个特定执行上下文所拥有的临时值，由该上下文把它计算为操作数；也可以“静置”，存储于某种内存中。

我们不需要过多关注临时值，因为它们的所有权规则很直接。临时值作为某个表达式的结果产生；该表达式会在某个特定位置使用；这个值在该位置需要，而在此之后不再需要；所以实现显然应该采取一切可能的措施，把值直接转发到该位置，而不是迫使它被复制。用户已经预期所有这些都会发生，这里其实没有什么可以改进的。

因此，我们对所有权的大部分讨论都会围绕内存中存储的值展开。Swift 对内存的处理涉及五个密切相关的概念。

*存储声明*是语言语法层面的概念，指在语言中可以像内存一样对待的声明。目前，它们总是通过 `let`、`var` 和 `subscript` 引入。存储声明具有类型，也有一份实现，用于定义读取或写入该存储意味着什么。`var` 或 `let` 的默认实现只是创建一个新变量来存储值，但存储声明也可以是计算式的，因此其背后未必存在任何变量。

*存储引用表达式*是语法层面的概念，指引用存储的表达式。它类似于其他语言中的“左值（l-value）”概念，只是它未必能用在赋值语句左侧，因为存储不一定可变。

*存储引用*是语言语义层面的概念，指对某项特定存储声明的完整引用。换句话说，它是在抽象层面求值存储引用表达式、但尚未实际访问存储时得到的结果。如果存储是成员，其中包括一个作为基值的值或存储引用。如果存储是下标，其中包括一个索引值。例如，像 `widgets[i].weight` 这样的存储引用表达式，可以在抽象层面求值得到如下存储引用：

* 局部变量 `var widgets: [Widget]` 的存储中，
* 索引值为 `19: Int` 的下标 `subscript(index: Int)` 的存储中，
* 属性 `var weight: Double` 的存储。

*变量*是语义层面的概念，指内存中用于存储一个值的唯一位置。至少在本文的用法中，它不一定可变。变量通常是为存储声明创建的，但也可以在原始内存中动态创建，例如使用 `UnsafeRawPointer`。变量始终具有特定类型。它还有一个*生命周期*，即语言语义中它开始存在的一个时点，以及它被销毁的一个（或多个）时点。

*内存位置*是一段连续的、可寻址的内存范围。在 Swift 中，这主要是一个实现层面的概念。Swift 不保证任何特定变量在其整个生命周期中都具有一致的内存位置，甚至不保证它一定存储于某个内存位置。不过，有时可以临时强制变量存在于一个特定且一致的位置，例如把它以 `inout` 方式传给 `withUnsafeMutablePointer`。

### 访问

对存储引用表达式的某一次具体求值称为一次访问。访问分为三种：*读取*、*赋值*和*修改*。赋值和修改都属于*写入*；区别在于，赋值会在不读取旧值的情况下完全替换旧值，而修改则依赖旧值。

所有存储引用表达式都会根据表达式所在的上下文，被归类为这三种访问之一。需要注意，这项决定是表层的：它只依赖直接上下文的语义规则，而不依赖对程序或其动态行为的深入分析。例如，作为 `inout` 参数传入的存储引用，在调用方始终按修改来求值，无论被调用方是否实际使用当前值、是否对其执行任何写入，甚至是否引用它。

存储引用表达式的求值分为两个阶段：首先将它正式求值为存储引用，然后在一段时间内对该存储引用发生一次正式访问。这两个阶段通常紧接着执行，但在复杂情况下可能分开，例如当 `inout` 参数不是某次调用的最后一个参数时。进行这种阶段划分，是为了在尽可能遵守 Swift 从左到右求值规则的同时，尽量缩短正式访问的持续时间。

## 独占法则

有了以上基础，就可以简洁地陈述本提案的第一部分——独占法则：

> 如果某个存储引用表达式求值得到由变量实现的存储引用，那么这次访问的正式访问期间，不得与对同一变量的任何其他访问的正式访问期间重叠，除非两次访问都是读取。

这里刻意采用了模糊表述：它只说访问“不得”重叠，却没有规定如何强制执行。这是因为，我们会针对不同种类的存储采用不同的执行机制。下一大节会讨论这些机制。不过在此之前，需要先从整体上讨论这条规则的一些影响，以及我们满足它的方法。

### 独占持续时间

法则规定，访问必须在整个正式访问期间保持独占。这个期间由引发访问的直接上下文决定；也就是说，它是程序的一项*静态*性质，而我们在引言中列出的安全问题是*动态*的。静态方法要解决动态问题，就只能以保守方式保证正确——这是普遍规律：会有一些动态层面合理的程序仍然遭到拒绝。我们完全有理由追问，这项普遍原则在这里如何体现。

例如，当存储作为 `inout` 参数传递时，访问会持续整个调用期间。这要求在调用方强制保证，调用期间不能对该存储发生任何其他访问。这是否可能过于粗粒度？毕竟，在被调用函数内部，可能有许多位置显然没有使用它的 `inout` 参数。或许我们应该在被调用方内部以更细的粒度跟踪对 `inout` 参数的访问，而不是尝试在调用方执行独占法则。问题在于，这种想法过于动态，无法高效实现。

针对 `inout` 的调用方规则有一项关键优势：调用方掌握了大量有关所传存储的信息。这意味着，调用方规则通常可以完全静态地执行，无须添加动态检查，也无须作出过度保守的假设。例如，假设某个函数对局部变量调用了一个 `mutating` 方法。（请记住，`mutating` 方法会把 `self` 作为 `inout` 参数传递。）除非该变量被逃逸闭包捕获，否则函数可以轻易检查对该变量的每次访问，确认它们都没有与这次调用重叠，从而证明规则得到满足。此外，这项保证随后会向下传递给被调用方，后者可以利用这些信息证明自身访问的安全性。

相比之下，针对 `inout` 的被调用方规则无法利用这类信息：这些信息在调用点会被直接丢弃。正如引言所述，这会导致我们今天看到的广泛优化问题。例如，假设被调用方先从参数加载一个值，随后调用一个优化器无法分析的函数：

```swift
extension Array {
  mutating func organize(_ predicate: (Element) -> Bool) {
    let first = self[0]
    if !predicate(first) { return }
    ...
    // something here uses first
  }
}
```

采用被调用方规则时，优化器必须把 `self[0]` 复制到 `first` 中，因为它必须（过度保守地）假定 `predicate` 可能以某种方式反过来修改 `self` 所绑定的变量。采用调用方规则时，只要优化器仍能证明数组没有被修改，就可以一直使用数组元素中保存的那份值。

此外，正如上面的例子所暗示的，如果接受被调用方规则，我们实际是在允许什么样的代码？像这样的高阶操作不应该担心调用方传入一个会以可重入方式修改数组的 predicate。简单的实现选择——例如在上例中创建局部变量 `first`，而不是再次访问 `self[0]`——都会变得具有语义意义；维护任何形式的不变量都会变得几乎不可想象。Swift 库通常禁止这种可重入访问，并不令人意外。但由于库不能彻底阻止程序员这样做，实现仍然必须在运行时执行额外工作，防止此类代码进入未定义行为并破坏进程。既然这些工作存在的唯一原因，是规避编写良好的程序中本就不应该出现的代码，我们认为放弃这种代码并不是真正的损失。

因此，本提案总体上主张采用调用方执行 `inout` 这类访问持续时间规则；它们只需付出很小的语义代价，就能创造大量优化机会。

### 值类型和引用类型的组成部分

前面多次谈到*变量*。读者完全有理由想知道，这一切对于*属性*意味着什么。

按照上文给出的定义，属性是一项存储声明，而存储属性会在其容器中创建一个对应变量。对这个变量的访问显然需要遵守独占法则；但属性被组织在同一个容器中这一事实，是否还会带来额外限制？具体来说，独占法则是否应该禁止对同一变量或值的不同属性进行重叠访问？

属性可以分为三组：

- 值类型的实例属性；
- 引用类型的实例属性；
- 任何类型上的 `static` 和 `class` 属性。

我们提议始终把引用类型属性和 `static` 属性视为彼此独立，但除了一种特定（且重要）的特殊情况之外，通常把值类型属性视为不独立。这可能是一项意义重大的限制，人们完全有理由追问它为何必要，以及为何需要在不同种类的属性之间作出这一区分。原因有三个。

#### 独立性与容器

第一个原因与容器有关。

对于值类型，既可以访问单个属性，也可以访问整个聚合值。很明显，对属性的访问可能与对聚合值的访问冲突，因为访问聚合值本质上就是同时访问所有属性。例如，设有一个变量（不一定是局部变量）`p: Point`，它包含存储属性 `x`、`y` 和 `z`。如果可以同时且独立地修改 `p` 与 `p.x`，独占法则中就会出现一个巨大的漏洞。因此，我们确实需要以某种方式在这里执行该法则。我们有三个选择。

（阅读有关执行该法则的主要章节之后，这部分内容可能更容易理解。）

第一种选择，是直接把访问 `p.x` 也视为访问 `p`。这可以干净利落地消除漏洞，因为针对 `p` 使用的任何执行机制都会自然阻止对它的冲突访问。但这也会阻止对不同属性的重叠访问，因为每次属性访问都会引发对 `p` 的访问，从而触发执行机制。

另外两种选择会反转这种关系。我们可以只为各个存储属性分别执行，而不对聚合值执行：对 `p` 的访问将被视为访问 `p.x`、`p.y` 和 `p.z`。或者，可以参数化执行机制，让它记录实际访问的属性路径，例如 `""`、`".x"` 等等。遗憾的是，这些方案存在两个问题。第一，我们并不总能知道完整的属性集合，也不总能知道哪些属性是存储属性；例如，由于泛型或韧性，类型的实现对我们来说可能是不透明的。对计算属性的访问必须视为对整个值的访问，因为它涉及以 `inout` 或 `shared` 方式把变量传给 getter 或 setter；因此，它确实会与所有其他属性冲突。若试图利用动态信息来克服这一点，就会把无处不在的记录工作引入值类型访问器，危及值类型作为低成本抽象工具的核心设计目标。第二，虽然这些方案可以相对容易地用于静态执行，但若用于动态执行，就需要在运行时完成复杂得可怕的大量记录工作；这与我们的性能目标完全不相容。

因此，确实存在一种方案，可以独立访问同一个聚合值的不同属性，但它要求我们对聚合访问使用静态执行，而且知道两个属性都是存储属性。这是一项重要的特殊情况，但终究只是特殊情况。在其他所有情形下，都必须退回到一般规则：访问属性也就是访问聚合值。

这些考虑不适用于 `static` 属性和引用类型的属性。Swift 中没有任何一种语言结构会同时访问一个类的每个属性；谈论某个类型的“所有”`static` 属性甚至没有意义，因为任意模块随时都可以为它新增一个。

#### 独立访问的惯用模式

第二个原因与用户预期有关。

禁止对值类型的不同属性进行重叠访问，至多只会带来一点小麻烦。独占法则本来就会阻止值类型上的“超距作用”：例如，对某个变量调用方法时，不可能触发一串不明显的事件，最终回头修改原变量，因为那会涉及对同一变量进行两次冲突且重叠的访问。

相比之下，许多成熟的引用类型模式恰恰依赖这种基于通知的更新。事实上，在 UI 代码中，同一个对象的不同属性并发修改并不少见：一个由 UI 修改，另一个由某项后台操作修改。禁止独立访问会破坏这些惯用模式，这是不可接受的。

至于 `static` 属性，程序员预期它们是相互独立的全局变量；因为访问一个全局变量而阻止访问另一个全局变量，没有任何道理。

#### 独立性与优化器

第三个原因与属性的优化潜力有关。

独占法则的部分目的，是允许对值执行一大类优化。例如，值类型上的非 `mutating` 方法可以假定 `self` 在整个方法执行期间保持完全不变。它无须担心中途调用的未知函数会以某种方式回头修改 `self`，因为这种修改会违反该法则。即使在 `mutating` 方法中，除非该方法自己知道，否则也没有代码能够访问 `self`。这些假设对于优化 Swift 代码极其重要。

然而，对于全局变量或引用类型属性中的内容，通常根本无法作出这些假设。类引用可以任意共享，优化器必须假定某个未知函数可能访问同一个实例。而且，系统中的任何代码都可能访问全局变量（暂不考虑访问控制）。因此，把对不同属性的访问视为不独立，语言实现几乎得不到任何收益。

#### 下标

这部分讨论大多也适用于下标，尽管在当前语言中，下标在技术上从来都不是存储式的。通过下标访问值类型的某个组成部分，会被视为访问整个值，因此也被认为会与对该值的任何其他访问重叠。它最重要的后果是，两个不同的数组元素不能同时访问。这会妨碍某些使用数组的常见惯用模式，不过，一些情形（例如并发修改数组的不同切片）在 Swift 中本来就相当棘手。我们认为，可以通过有针对性地改进集合 API，缓解这里的大部分影响。

## 执行独占法则

执行独占法则有三种可用机制：静态执行、动态执行和未定义执行。采用哪种机制，必须能够通过简单检查存储声明来决定，因为声明的定义和所有直接访问器必须就执行方式达成一致。一般来说，选择取决于所声明存储的种类、它的容器（如果有），以及可能存在的任何特性。

### 静态执行

在静态执行机制下，编译器会检测到违反法则的情况并报告错误。只要可行，这就是首选机制，因为它安全、可靠，而且不产生运行时成本。

只有当问题能够完全判定时，才能使用这种机制。例如，它可以用于值类型属性，因为递归应用独占法则能够保证基存储正被独占访问。它不能用于普通引用类型属性，因为通常无法证明某个特定对象引用是指向该对象的唯一引用。不过，如果支持唯一引用的类类型，就可以对它们的属性使用这种机制。

在某些需要的情况下，编译器或许可以通过隐式插入复制来保留源代码兼容性并避免报错。这很可能只会在源代码兼容模式中采用。

静态执行将用于：

- 所有种类的不可变变量；

- 局部变量，但使用闭包所产生的影响除外（见下文）；

- `inout` 参数；以及

- 值类型的实例属性。

### 动态执行

在动态执行机制下，实现会记录每个变量当前是否正被访问。如果检测到冲突，就会触发动态失败。如果编译器发现动态执行一定会检测出冲突，也可以直接静态报错。

这项记录工作为每个变量需要两个比特，用来表达“未访问”“读取”和“修改”三种状态。虽然可以同时存在多个读取，但通过一点巧妙处理，在访问期间保存旧状态，就能避免维护完整计数。

这套记录机制旨在尽力而为。它应该可靠地检测确定性违规，但不要求检测竞态条件；它往往确实能检测出来，这很好，却不是强制要求。它*必须*正确处理并发读取，例如不能把记录永久留在“读取”状态。不过，在仍有活跃读取者时，并发读取情形把记录留在“未访问”状态也是可以接受的；这使记录机制可以使用非原子操作。但是，如果为了记录一个类的不同属性等情况而把多项记录打包到一个字节中，就必须使用原子操作，因为同一个类中不同变量之间允许并发访问。

如果编译器检测到某次访问是“瞬时的”——也就是说，访问期间执行的代码绝不可能引发对同一变量的可重入访问——就可以避免更新记录，只检查其值是否适当。这在读取中很常见，因为读取通常只会在访问期间复制值。当编译器检测到所有可能访问都是瞬时的，例如变量是 `private` 或 `internal` 时，就可以消除全部记录。我们预计这种情况会相当常见。

动态执行将用于：

- 因使用闭包而有必要时的局部变量（见下文）；

- 类类型的实例属性；

- `static` 和 `class` 属性；以及

- 全局变量。

我们应该提供一个特性，允许特定属性或类把动态执行降级为未定义执行。一些客户端很可能会认为动态执行对性能的影响过大，因此提供退出选项非常重要。在这项特性推出初期尤其如此，因为当时我们仍在探索不同实现方案，也尚未实现任何整体优化。

未来围绕类实例隔离开展的工作，或许能让我们对某些类实例属性使用静态执行。

### 未定义执行

未定义执行意味着冲突既不会静态检测，也不会动态检测，而是直接产生未定义行为。考虑到 Swift“默认安全”的设计，这不是普通代码所期望的机制，但对于不安全指针之类的内容，这是唯一现实的选择。

未定义执行将用于：

- 不安全指针的 `memory` 属性。

### 对闭包捕获的局部变量执行法则

我们能够静态执行独占法则，依赖于我们能够静态推理使用发生在何处。对于局部变量，这项分析通常很直接；但当变量被闭包捕获时，通往该次使用的控制流可能被遮蔽，分析就会变得复杂。即使已知闭包不会逃逸，它仍有可能以可重入或并发方式执行。适用以下原则：

- 如果闭包 `C` 有可能逃逸，那么对于 `C` 捕获的任何变量 `V`，除非所有访问都是读取，否则所有可能在潜在逃逸之后执行的对 `V` 的访问（包括 `C` 内部的访问）都必须使用动态执行。

- 如果闭包 `C` 不会逃逸出函数，那么函数内部使用它的位置是已知的；在每个位置上，闭包要么被直接调用，要么被作为参数用于另一次调用。考虑每次这种调用中使用的一组非逃逸闭包。对于 `C` 捕获的每个变量 `V`，如果其中任何闭包包含对 `V` 的写入，那么这些闭包内的所有访问都必须使用动态执行，而且在静态执行时把这次调用视为对 `V` 的写入；否则，这些访问可以使用静态执行，并把这次调用视为对 `V` 的读取。

这些规则很可能可以逐步改进。例如，对于直接调用闭包的规则，我们应该能够做得更好。

## 显式所有权工具

### 共享值

本节的许多讨论都涉及*共享值*这一新概念。顾名思义，共享值是由程序中拥有它的另一部分共享给当前上下文的值。为了符合独占法则，因为程序中的多个部分可以同时使用该值，它在所有这些部分（甚至包括拥有它的上下文）中都必须是只读的。这个概念让程序能够在不复制值的情况下对值进行抽象，就像 `inout` 让程序能够对变量进行抽象一样。

（熟悉 Rust 的读者会看到，共享值与 Rust 的不可变借用概念有许多相似之处。）

如果共享值来源于存储引用，它实际上就像指向该存储的不可变引用。在共享值的整个持续期间，存储都会作为读取被访问，因此独占法则能够保证访问期间没有其他访问可以修改原变量。某些种类的共享值也可以绑定到临时值（即右值）。由于临时值始终由当前执行上下文拥有，并且只在一个位置使用，这不会带来额外的语义问题。

共享值可以像普通参数或 `let` 绑定一样，在绑定它的作用域中使用。如果共享值用在需要所有权的位置，Swift 会直接隐式复制该值——同样，就像普通参数或 `let` 绑定一样。

#### 共享值的局限

本文这一节描述了形成和使用共享值的几种方式。然而，当前设计并没有提供一般性的、“一等”的共享值操作机制。程序不能返回共享值，不能构造共享值数组，不能把共享值存入 `struct` 字段，等等。这些限制类似于 `inout` 引用已有的限制。事实上，二者的相似之处如此普遍，以至于需要一个同时涵盖它们的术语：我们称之为*短暂值（ephemerals）*。

我们的设计没有试图为短暂值提供一等设施，这是经过慎重考虑的决定，源于三方面顾虑：

- 我们必须把这份提案限定在未来数月内有可能实现的范围。我们预计它会为语言及其实现带来重大收益，但它已经相当宽泛且激进。一等短暂值会给实现和设计增加足够多的复杂度，显然超出范围。此外，剩余的语言设计问题非常庞大；已有多种语言尝试过一等短暂值，而结果并不完全令人满意。

- 类型系统用复杂性换取表达能力。总可以通过让类型系统更复杂来接受更多程序，但这并不总是一笔划算的交易。Rust 等语言中一等引用背后的生命周期限定系统，给用户模型增加了大量复杂性。这种复杂性会给用户带来真实成本。而且，为了绕过所有权系统的局限，有时仍不可避免地需要退回不安全代码。既然无论如何都必须在某处划一条界线，那么生命周期限定系统是否值得放在界线的 Swift 一侧，尚无定论。

- 类似 Rust 的生命周期系统在 Swift 中未必能像在 Rust 中一样强大。Swift 有意提供一种语言模型，为类型作者和 Swift 编译器本身保留了大量实现灵活性。

  例如，Swift 中的多态存储比 Rust 灵活得多。Swift 的 `MutableCollection` 必须实现一个 `subscript`，为给定索引提供元素访问器，但其实现几乎可以采用任意方式。如果泛型代码访问这个 `subscript`，而它恰好以直接访问底层内存的方式实现，那么访问会原地发生；但如果 `subscript` 通过计算式 getter 和 setter 实现，那么访问会在临时变量中发生，并根据需要调用 getter 和 setter。之所以能这样做，只因为 Swift 的访问模型具有很强的词法性质，并且保留了在访问结束时运行任意代码的能力。想象一下，要实现一个循环，把这些临时可变引用加入数组，需要做些什么——循环的每次迭代都必须能够排队安排任意代码，在函数结束使用该数组时作为清理操作运行。这几乎算不上低成本抽象！一个更类似 Rust、且符合生命周期规则的 `MutableCollection` 接口，必须承诺 `subscript` 返回指向既有内存的指针；这样就完全无法采用计算式实现。

  即使是简单的 `struct` 成员，也会出现类似问题。Rust 的生命周期规则规定，如果拥有指向某个 `struct` 的指针，就可以创建指向该 `struct` 中某个字段的指针，并且它与原指针具有相同的生命周期。但这不仅假定字段确实存储在内存中，还假定它以*简单*方式存储，因此可以创建一个指向它的简单指针，而且该指针遵循该类型指针的标准 ABI。这意味着 Rust 不能使用诸如把多个布尔字段打包进一个字节，甚至只是降低字段对齐要求等布局优化。Swift 不愿作出这样的保证。

由于以上所有原因，虽然从理论上说，我们仍有兴趣探索更复杂的系统，以允许短暂值具有更广泛的用法，但现在并不提议承担这项工作。由于这种系统主要由类型系统修改构成，我们不担心它长期会引发 ABI 稳定性问题，也不担心会遭遇源代码不兼容；我们认为，这里的任何增强都可以作为对提议特性的扩展和泛化来完成。

### 局部短暂绑定

Swift 除了把存储作为 `inout` 参数传递之外，没有其他方式对存储进行抽象；这已经是一项有些荒唐的限制。它很容易绕过，因为想要局部 `inout` 绑定的程序员只需引入一个闭包并立即调用它，但用这种笨拙方式实现本该相当容易的事情，并不理想。

共享值让这项限制更加明显，因为局部共享值是局部 `let` 的一种有趣替代方案：它以阻止对原始存储进行其他访问为代价，避免一次复制。我们不鼓励程序员在所有代码中都使用 `shared` 取代 `let`，尤其是因为优化器通常本就能够消除复制。不过，优化器并非总能移除复制，因此在少数场景下，`shared` 这种微优化可能有用。此外，使用不可复制类型时，消除形式上的复制在语义上也可能是必要的。

我们提议以直接的方式移除这项限制：

```swift
inout root = &tree.root

shared elements = self.queue
```

初始值设定项是必需的，而且必须是存储引用表达式。访问会持续作用域余下的整个期间。

### 函数参数

函数参数是程序对值进行抽象的最重要方式。Swift 目前提供三种参数传递方式：

- 按值传递、由被调用方拥有。这是普通参数采用的规则，无法显式写出。

- 按值传递、共享。这是 `nonmutating` 方法的 `self` 参数所采用的规则，无法显式写出。

- 按引用传递。这是 `inout` 参数和 `mutating` 方法的 `self` 参数所采用的规则。

这里的提议只是允许显式写出非标准情况：

- 函数参数可以显式声明为 `owned`：

  ```swift
  func append(_ values: owned [Element]) {
    ...
  }
  ```

  它不能与 `shared` 或 `inout` 结合使用。

  这只是显式写出默认规则的方式；除非使用不可复制类型，否则我们预计用户不会经常这样写。

- 函数参数可以显式声明为 `shared`。

  ```swift
  func ==(left: shared String, right: shared String) -> Bool {
    ...
  }
  ```

  它不能与 `owned` 或 `inout` 结合使用。

  如果函数参数是存储引用表达式，那么相应存储会在整个调用期间作为读取被访问。否则，参数表达式会作为右值求值，并在调用期间共享该临时值。允许函数参数共享临时值非常重要，因为许多函数参数会被标记为 `shared`，只是因为函数实际上无法从拥有该参数中受益，并不是因为它们在语义上一定要接收指向既有变量的引用。例如，我们预计会把比较运算符之类的内容改为以 `shared` 方式接收参数，因为必须能够在不取得不可复制值的情况下比较它们；但这不应该阻止程序员拿某个值与字面量进行比较。

  与 `inout` 一样，这是函数类型的一部分。与 `inout` 不同，大多数函数兼容性检查（例如覆盖检查和函数转换检查）在 `shared` / `owned` 不匹配时应该仍能通过。如果带 `owned` 参数的函数被转换为（或覆盖）带 `shared` 参数的函数，那么参数类型实际上必须可复制。

- 方法可以显式声明为 `consuming`。

  ```swift
  consuming func moveElements(into collection: inout [Element]) {
    ...
  }
  ```

  这会让 `self` 作为 owned 值传递，因此不能与 `mutating` 或 `nonmutating` 结合。

  在方法内部，`self` 仍然是不可变绑定。

### 函数结果

正如本节开头所述，Swift 的词法访问模型无法很好地扩展到允许函数返回短暂值。执行一次访问，需要在访问开始和结束时分别执行存储特有的代码。函数返回之后，就再也没有能力继续执行代码。

可以设想，让函数在返回短暂值的同时返回一个回调，并期望调用方用完短暂值时执行该回调。然而，只有这一点还不够，因为被调用方可能依赖其调用方提供的保证。例如，考虑一个 `struct` 上的 `mutating` 方法，它想返回指向某个存储属性的 `inout` 引用。它是否正确，不仅取决于该方法能否完成对属性访问的清理工作，也取决于 `self` 所绑定变量是否继续有效。我们真正希望的，是保留被调用方中的当前上下文，以及调用方中的全部活跃作用域，然后直接在调用方中进入一个新的嵌套作用域，把短暂值作为某种参数。但这是编程语言中一种广为理解的情形：它就是一种协程。（由于存在作用域限制，也可以把它看作回调函数的语法糖，其中的 `return`、`break` 等会真正按预期工作。）

事实上，协程很适合解决多种与短暂值有关的问题。接下来的几个小节会探讨这一思路。

### `for` 循环

正如有三种值得关注的参数传递方式，也可以识别出三种值得关注的序列迭代方式。每一种都可以通过 `for` 循环表达。

#### 消费式迭代

第一种迭代方式是 Swift 中已经熟悉的消费式迭代：每一步都会获得一个 owned 值。对于值可能按需创建的任意序列，这是唯一可行的迭代方式。它对于处理不可复制类型的集合也很重要，因为它允许解构集合，并让循环取得元素的所有权。由于它会取得序列所产生值的所有权，而且任意序列不能多次迭代，因此这是对 `Sequence` 的一项 `consuming` 操作。

可以把迭代变量声明为 `owned` 来显式请求：

```swift
for owned employee in company.employees {
  newCompany.employees.append(employee)
}
```

如果不满足非修改式迭代的要求，也会隐式采用这种方式。（除此之外，这是保持源代码兼容性所必需的。）

接下来两种方式只对集合有意义。

#### 非修改式迭代

非修改式迭代只是逐一访问集合中的每个元素，让集合保持完整且不被修改。没有理由复制元素；迭代变量可以直接绑定到共享值。这是对 `Collection` 的一项 `nonmutating` 操作。

可以把迭代变量声明为 `shared` 来显式请求：

```swift
for shared employee in company.employees {
  if !employee.respected { throw CatastrophicHRFailure() }
}
```

如果已知序列类型遵循 `Collection`，默认也会使用这种方式，因为这是遍历集合的最优方式。

```swift
for employee in company.employees {
  if !employee.respected { throw CatastrophicHRFailure() }
}
```

如果序列操作数是存储引用表达式，相应存储会在整个循环期间被访问。注意，这意味着独占法则会隐式阻止迭代期间修改集合。程序可以对操作数使用 `copy` 内建函数，显式请求遍历该存储中值的一个副本。

#### 修改式迭代

修改式迭代会访问每个元素，并可能对其进行修改。迭代变量是指向该元素的 `inout` 引用。这是对 `MutableCollection` 的一项 `mutating` 操作。

必须把迭代变量声明为 `inout` 来显式请求：

```swift
for inout employee in company.employees {
  employee.respected = true
}
```

序列操作数必须是存储引用表达式。相应存储会在整个循环期间被访问，这会（如上所述）阻止对集合的任何其他重叠访问。（不过，如果集合类型把这项操作定义为非修改操作，例如引用语义的集合可能会这样做，那么此规则不适用。）

#### 表达修改式与非修改式迭代

修改式和非修改式迭代要求集合在每一步都产生短暂值。语言可以用多种方式表达这一点，其中一种合理方案是使用协程。由于协程向调用方让出一个值时并不会放弃自身的执行上下文，因此允许协程多次让出值是合理的，这与循环的基本代码模式非常契合。由此产生的协程通常称为生成器；多种主流语言都用它便捷地实现迭代。在 Swift 中，若要遵循这种模式，就需要允许定义生成器函数，例如：

```swift
mutating generator iterateMutable() -> inout Element {
  var i = startIndex, e = endIndex
  while i != e {
    yield &self[i]
    self.formIndex(after: &i)
  }
}
```

在客户端一侧，如何用它实现 `for` 循环很清楚；不那么清楚的是，应该如何允许代码直接使用生成器。这里，协程的使用方式受到一些值得关注的约束，因为正如上文所述，整个协程在逻辑上都必须在对基值的一次访问作用域内执行。如果生成器函数像常见设计那样实际返回某种生成器对象，编译器就必须确保该对象不会逃逸出外层访问。这会产生大量复杂性。

### 泛化访问器

如今 Swift 为实现属性和下标提供的工具非常粗糙，本质上只有 `get` 和 `set` 方法。在性能至关重要的任务中，这些工具并不充分，因为它们无法在没有复制的情况下直接访问值。标准库可以使用一组稍丰富的工具，在有限场景下提供这种直接访问，但它们仍然相当薄弱；出于多种原因，我们一直不愿把它们公开给用户。

所有权为我们提供了重新审视这个问题的机会，因为 `get` 无法用于不可复制类型的集合：它会返回一个值，因此必须拥有该值。访问器真正需要的，是能够让出共享值，而不是返回 owned 值。同样，一种合理的实现方式是使用特殊种类的协程。与生成器不同，这种协程必须且只能让出一次值。而且，无须设计一种让程序员显式调用它的方式，因为它只会用于访问器。

思路是，存储声明可以不定义 `get` 和 `set`，而定义 `read` 和 `modify`：

```swift
var x: String
var y: String
var first: String {
  read {
    if x < y { yield x }
    else { yield y }
  }
  modify {
    if x < y { yield &x }
    else { yield &y }
  }
}
```

存储声明必须定义 `get` 或 `read` 之一（或者本身是存储属性），但不能同时定义二者。

若要可变，存储声明还必须定义 `set` 或 `modify` 之一。它也可以选择*同时*定义二者；在这种情况下，赋值会使用 `set`，修改会使用 `modify`。这有助于优化某些复杂的计算属性，因为它允许原地执行修改，而不会迫使简单赋值先读取旧值；不过，必须谨慎确保 `modify` 的行为与 `get` 和 `set` 一致。

### 内建函数

#### `move`

Swift 优化器通常会尝试移动值而不是复制值，但有时强制它这样做也很有用。因此，我们提议添加 `move` 函数。从概念上说，`move` 只是 Swift 标准库中的一个顶层函数：

```swift
func move<T>(_ value: T) -> T {
  return value
}
```

不过，它被赋予了一些特殊语义。它不能间接使用。参数表达式必须引用某种局部拥有型存储：`let`、`var` 或 `inout` 绑定。对 `move` 的调用会在语义上把当前值移出参数变量，并把它作为表达式类型的值返回；对于确定初始化分析而言，变量随后处于未初始化状态。接下来变量会发生什么，取决于其种类：

- `var` 直接回到未初始化状态。在给它赋新值并由此重新初始化之前，使用它是非法的。

- `inout` 绑定与 `var` 类似，区别在于它不能在未初始化状态下离开作用域。也就是说，如果程序把值移出 `inout` 绑定，就必须先为其赋新值，才能以任何方式退出作用域（包括抛出错误）。注意，让 `inout` 暂时处于未初始化状态是否安全，取决于独占法则。

- `let` 不能重新初始化，因此再也不能使用。

这应该可以直接加入既有的确定初始化分析；该分析负责证明局部变量在使用前已经初始化。

#### `copy`

`copy` 是 Swift 标准库中的一个顶层函数：

```swift
func copy<T>(_ value: T) -> T {
  return value
}
```

参数必须是存储引用表达式。其语义完全如上面代码所示：返回参数值。它有几个用途：

- 它可以抑制语法上的特殊处理。例如，如上所述，如果 `shared` 参数是存储引用，相应存储通常会在整个调用期间被访问。程序员可以事先对存储引用调用 `copy`，从而抑制这种行为，并强制复制在调用之前完成。

- 对于禁止隐式复制的类型，它是必需的。请参阅下文有关不可复制类型的章节。

#### `endScope`

`endScope` 是 Swift 标准库中的一个顶层函数：

```swift
func endScope<T>(_ value: T) -> () {}
```

参数必须引用局部 `let`、`var`，或者独立的（非参数、非循环）`inout` 或 `shared` 声明。如果它是 `let` 或 `var`，变量会立即销毁。如果它是 `inout` 或 `shared`，访问会立即结束。

确定初始化分析必须证明该声明在这次调用之后不再使用。如果存储是被逃逸闭包捕获的 `var`，则属于错误。

它可以用来在控制流到达作用域末尾之前结束访问，也可用于对值的销毁进行微优化。

`endScope` 保证，在执行这次调用时，给定变量已经销毁，或者给定访问已经结束。它并不承诺这些事情恰好发生在该点：实现仍然可以更早结束它们。

### 透镜

目前，Swift 中所有存储引用表达式都是*具体的*：每个组成部分都能静态解析为某项存储声明。社区中不断有人希望允许程序对存储进行抽象，以便编写：

```swift
let prop = Widget.weight
```

随后，`prop` 将成为对 `weight` 属性的抽象引用，其类型大致会是 `(Widget) -> Double`。

这项特性与所有权模型有关，因为普通函数结果必须是 owned 值：既不能是 shared，也不能可变。这意味着，透镜只能用于抽象*读取*而非*写入*，而且只能针对可复制属性创建。这还意味着，使用透镜的代码会比使用具体存储引用的等价代码涉及更多复制。

假设透镜不是简单函数，而是自身构成一种值类型。应用透镜会得到一个存储引用表达式，但它是访问静态未知成员的*抽象*表达式。这要求语言实现能够动态执行这种访问。不过，访问未知属性的问题，与访问实现未知的已知属性非常相似；也就是说，为了实现泛型和韧性，语言已经必须完成非常相似的工作。

总体而言，这样的特性会非常自然地融入这里阐述的所有权模型。

## 不可复制类型

不可复制类型在多种专家级场景中很有用。例如，它们可以高效表达唯一所有权。它们也适合表达具有某种独立身份的值，例如原子类型。还可以把它们作为一种正式机制，鼓励代码更高效地处理复制成本可能很高的类型，例如大型结构体类型。共同主题是：我们不希望允许类型被隐式复制。

在 Swift 中处理不可复制类型的复杂性主要来自两个方面：

- 语言必须提供移动和共享值而不强制复制的工具。本文已经提出这些工具，因为它们对于优化可复制类型的使用同样重要。

- 泛型系统必须能够表达针对不可复制类型的泛型，同时又不大规模破坏源代码兼容性，也不把不可复制类型强加给所有人。

除此之外，这项特性本身相当小。编译器会隐式生成移动而不是复制，就像前面针对 `move` 内建函数所讨论的那样，然后诊断无法这样工作的情况。

### `moveonly` 上下文

不过，泛型问题确实存在。在 Swift 中为可复制性建模，最明显的方式是定义一个类型可以遵循的 `Copyable` 协议。这样一来，就不会假定无约束的类型参数 `T` 可复制。遗憾的是，这对源代码兼容性和易用性都会造成灾难，因为 Swift 中几乎所有现有泛型代码都假定类型可复制；我们实在不希望程序员第一次接触泛型代码时，就不得不操心不可复制类型。

此外，我们不希望类型必须显式声明遵循 `Copyable`。可复制应该是默认情况。

合乎逻辑的解决方案是继续维持“所有类型默认可复制”这一假设，然后允许特定上下文关闭该假设。我们把这些上下文称为 `moveonly` 上下文。词法上嵌套在 `moveonly` 上下文中的所有上下文，也都隐式成为 `moveonly`。

一个类型可以成为 `moveonly` 上下文：

```swift
moveonly struct Array<Element> {
  // Element and Array<Element> are not assumed to be copyable here
}
```

这会针对所声明的类型、它的泛型实参（如果有）以及这些泛型实参的关联类型层级，取消可复制性假设。

扩展可以成为 `moveonly` 上下文：

```swift
moveonly extension Array {
  // Element and Array<Element> are not assumed to be copyable here
}
```

类型可以通过条件遵循来声明有条件的可复制性：

```swift
moveonly extension Array: Copyable where Element: Copyable {
  ...
}
```

无论是否有条件，遵循 `Copyable` 都是类型的一项固有性质，必须在定义该类型的同一个模块（甚至可能要求同一个文件）中声明。

类型的非 `moveonly` 扩展会为该类型及其泛型实参重新引入可复制性假设。这是允许标准库类型支持不可复制元素、同时又不破坏与既有扩展兼容性所必需的。如果类型没有声明任何 `Copyable` 遵循，为它添加非 `moveonly` 扩展就是错误。

函数可以成为 `moveonly` 上下文：

```swift
extension Array {
  moveonly func report<U>(_ u: U)
}
```

这会针对任何新的泛型实参及其关联类型层级，取消可复制性假设。

`moveonly` 上下文的许多细节仍悬而未决。我们很可能需要积累大量实现经验，才能真正确定正确的设计。

我们正在考虑的一种可能性，是让 `moveonly` 上下文也取消对可复制类型值的隐式可复制性假设。这会为那些必须极其谨慎对待复制的代码提供一种重要优化工具。

### 不可复制类型的 `deinit`

声明为 `moveonly` 且不遵循 `Copyable`（即使有条件遵循也不行）的值类型，可以定义 `deinit` 方法。`deinit` 必须定义在主类型定义中，而不能定义在扩展中。

当值不再需要时，会调用 `deinit` 销毁该值。这使不可复制类型能够表达资源的唯一所有权。例如，下面是一个简单的文件句柄类型，可以确保值被销毁时关闭句柄：

```swift
moveonly struct File {
  var descriptor: Int32

  init(filename: String) throws {
    descriptor = Darwin.open(filename, O_RDONLY)

    // Abnormally exiting 'init' at any point prevents deinit
    // from being called.
    if descriptor == -1 { throw ... }
  }

  deinit {
    _ = Darwin.close(descriptor)
  }

  consuming func close() throws {
    if Darwin.fsync(descriptor) != 0 { throw ... }

    // This is a consuming function, so it has ownership of self.
    // It doesn't consume self in any other way, so it will
    // destroy it when it exits by calling deinit.  deinit
    // will then handle actually closing the descriptor.
  }
}
```

Swift 可以在值最后一次使用之后、形式上的销毁点之前的任意时刻销毁该值（并由此调用 `deinit`）。为了这一定义，究竟什么算作“使用”，目前还没有完全决定。

如果值类型是 `struct`，那么在 `deinit` 中只能使用 `self` 来引用该类型的存储属性。对于确定初始化分析而言，`self` 的存储属性会像局部 `let` 常量一样处理；也就是说，它们由 `deinit` 拥有，可以被移出。

如果值类型是 `enum`，那么在 `deinit` 中只能把 `self` 用作 `switch` 的操作数。在这个 `switch` 内，任何关联值都会用于初始化相应绑定，而这些绑定会取得关联值的所有权。这样的 `switch` 会让 `self` 处于未初始化状态。

### 显式可复制类型

在不可复制类型这一领域，我们探索的另一个想法是：允许声明某个类型不能被隐式复制。例如，一个非常大的结构体在形式上可以复制，但不必要的复制可能对性能产生超出比例的影响。这样的类型应该遵循 `Copyable`，也应该能够通过 `copy` 函数请求复制；但编译器应该像诊断不可复制类型的复制一样，诊断任何隐式复制。

## 实现优先级

本文列出了大量工作，可以概括如下：

- 执行独占法则：

  - 静态执行
  - 动态执行
  - 优化动态执行

- 新标注和声明：

  - `shared` 参数
  - `consuming` 方法
  - 局部 `shared` 和 `inout` 声明

- 影响确定初始化（DI）的新内建函数：

  - `move` 函数及其对 DI 的影响
  - `endScope` 函数及其对 DI 的影响

- 协程特性：

  - 泛化访问器

### ABI 稳定性的优先事项

未来几个版本最重要的单一目标是 ABI 稳定性。这些特性的优先级排序和分析，必须以它们对 ABI 的影响为中心。考虑到这一点，主要的 ABI 注意事项如下：

独占法则会影响 ABI，因为它改变了针对参数作出的保证。必须在锁定 ABI 之前采用这条规则，否则我们会永远困在保守假设中。不过，它的具体执行细节不会影响 ABI，除非我们选择把部分工作卸载给运行时；这既非必要，也可以在未来版本中修改。（从技术上说，独占法则很可能会对优化器产生重大影响；但这只是一般的项目排期考虑，而不是影响 ABI 的事项。）

标准库很可能会积极地在参数上采用所有权标注。这些标注会影响相应库例程的 ABI。库开发者需要时间来采用它们；但更重要的是，他们需要某种方法验证这些标注是否有用。遗憾的是，最好的验证方式是实现不可复制类型，而除此以外，不可复制类型在优先级列表中非常靠后。

泛化访问器工作包括，把属性和下标的标准“最通用”访问器集合从 `get`/`set`/`materializeForSet` 改为（实质上的）`read`/`set`/`modify`。这会影响所有多态属性和下标访问的基本 ABI，因此必须完成。不过，完成这项 ABI 修改，并不要求真正迈出允许在 Swift 中定义协程式访问器的那一步。重要的是确保最终确定的 ABI 足以在未来支持协程。

生成器工作可能涉及修改核心集合协议。这肯定会影响 ABI。与泛化访问器不同，要完成这项工作，我们绝对需要实现生成器。

不可复制类型和算法只有在标准库采用它们时才会影响 ABI。如果标准库要在标准集合中广泛采用它们，就必须在稳定 ABI 之前完成。

新的局部声明和内建函数不会影响 ABI。（常见的情况是，影响最少的工作也恰好是最容易的一部分。）

在标准库中采用所有权和不可复制类型很可能需要大量工作，但这对不可复制类型的易用性非常重要。如果无法创建不可复制类型的 `Array`，这项特性就会受到很大限制。
