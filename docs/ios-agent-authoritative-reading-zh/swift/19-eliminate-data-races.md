# 用 Swift 并发消除数据竞争

- **Original title**: Eliminate data races using Swift Concurrency
- **原文链接**: [Apple Developer](https://developer.apple.com/videos/play/wwdc2022/110351/)
- **作者/机构**: Douglas Gregor / Apple Swift 团队
- **年份**: 2022
- **材料类型**: WWDC 并发安全演讲与文字稿
- **文档性质**: 忠实中文精读，不是原文全文翻译

## 文章要解决的问题

会写 `async` 并不代表程序没有数据竞争。安全取决于可变状态属于哪个隔离域、哪些值能跨域传递，以及闭包可能在哪里并发执行。原文从这些边界出发，说明 Swift 编译器如何发现潜在的不安全共享，并强调数据竞争安全与业务逻辑正确不是同一层问题。

## 原文论证主线

演讲把并发代码划分为 task isolation、actor isolation 和未隔离的可发送值。task 的局部状态不应在仍可能并发访问时被逃逸闭包共享；actor 状态只能由相应隔离域访问；跨域传递的值需要满足 `Sendable`，并发执行闭包用 `@Sendable` 限制捕获。随后文章讨论 actor 操作的原子区段、`await` 后重入，以及不能依赖任务提交顺序推断完成顺序。

## 关键机制与结论

`Sendable` 是关于值能否安全越过并发边界的语义承诺，不是“线程安全类”的装饰标签。纯值数据通常容易满足；内部共享可变引用则需不可变设计、同步保护或限制隔离域。Actor 方法在连续同步片段内受隔离保护，但跨越 `await` 后不再是一个原子事务。编译器能阻止许多别名泄漏，程序仍需设计取消、失败、顺序和状态机。

## 准确性与版本边界

原文展示的是 Swift 5.7 时代逐步启用的严格检查。Swift 5.10 已能以 complete 模式检查，Swift 6 language mode 把相应问题提升为错误，区域隔离等分析又减少了部分误报。即便通过检查，unsafe 指针、未标注旧框架、Objective-C 共享状态和外部系统仍可能引入竞争；actor 重入、死锁和时序错误也不等同于语言所说的数据竞争。

## 在知识体系中的位置

它是并发主干的安全模型篇：结构化并发定义任务关系，actor 定义状态隔离，本篇解释值如何安全跨边界。阅读后再看运行时幕后，可以避免把编译期隔离概念误解成固定线程或队列规则。
