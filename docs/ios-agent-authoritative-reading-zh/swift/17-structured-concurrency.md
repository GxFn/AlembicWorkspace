# 探索 Swift 结构化并发

- **Original title**: Explore structured concurrency in Swift
- **原文链接**: [Apple Developer](https://developer.apple.com/videos/play/wwdc2021/10134/)
- **作者/机构**: Kavon Farvardin、Joe Groff / Apple Swift 团队
- **年份**: 2021
- **材料类型**: WWDC 并发设计演讲与文字稿
- **文档性质**: 忠实中文精读，不是原文全文翻译

## 文章要解决的问题

回调和任意启动的后台工作会让控制流、错误、取消和生命周期彼此分离。结构化并发希望像结构化控制流约束跳转一样，用词法作用域约束并发子任务，使“这批工作何时结束、失败如何传播、谁负责取消”能从代码结构中读出来。

## 原文论证主线

演讲先把 task 视为异步工作的基本单元，再介绍两种结构化创建方式。`async let` 适合数量在代码中固定的并行子结果；task group 适合运行时动态加入子任务并逐个收集结果。子任务处于父任务的作用域内，父任务离开结构前必须处理它们。错误、优先级和取消状态能够沿任务关系传播，使运行时掌握依赖图。

## 关键机制与结论

结构化任务形成树，而不是彼此失联的线程。`await` 是潜在挂起点：任务可暂停并释放执行线程，但不保证每次都实际挂起。取消是协作式状态与传播机制，不会强制杀死任务；算法应检查取消或调用会响应取消的异步 API。非结构化 `Task` 有合理用途，例如把同步入口接入异步世界，但其句柄、生命周期、错误与取消责任必须由代码显式管理；detached task 还会放弃更多上下文继承。

## 准确性与版本边界

材料对应 Swift 5.5，核心任务树语义仍有效，但 Swift 6 的数据竞争检查、隔离推断和 Swift 6.2 的执行上下文规则改变了部分诊断与默认行为。task 不等于 thread，创建一万个 task 也不是创建一万个线程；运行在哪条线程、何时调度及完成顺序都不是 API 保证。结构化并发同样不能自动修复算法级竞态。

它是 Swift 并发主干的第一篇，回答任务如何组织。接下来应读 actor 文章理解共享状态隔离，再读数据竞争和运行时文章，分别补齐编译期安全模型与底层执行模型。
