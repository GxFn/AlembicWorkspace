# 现代 Objective-C Runtime 如何压缩内存

- **原文链接**: [原文](https://developer.apple.com/videos/play/wwdc2020/10163/)
- **作者 / 机构**: Ben / Apple Languages and Runtimes Team
- **年份**: 2020
- **材料类型**: Apple WWDC 技术演讲
- **文档性质**: 忠实中文精读，不是原文全文翻译

## 文章要解决的问题

这场演讲不仅介绍 2020 年的三项内存优化，更借真实兼容性事故回答：Runtime 为什么必须隐藏内部结构；应用直接读取类、方法列表或 Tagged Pointer 位布局时，为何一次系统升级就可能崩溃或静默破坏数据。

## 原文论证主线

第一部分从 clean memory 与 dirty memory 的成本差异出发。类的只读信息可从二进制重新载入，而运行时会变化的数据必须常驻。旧设计为每个已使用类分配较大的 `class_rw_t`；设备统计显示真正修改过方法的类只占少数，于是 Apple 把少用字段拆到按需扩展记录中，减少大量脏内存。

第二部分处理方法列表。每个方法记录 selector、类型编码和 IMP，64 位绝对指针既占空间又需要加载时修正。由于编译期方法实现位于同一镜像附近，工具链可用 32 位相对偏移表示，降低表大小并避免部分 fixup。运行时 Swizzling 仍可指向任意位置，因此另用稀疏映射记录被替换的实现。

第三部分解释 Tagged Pointer：把小值直接编码进指针空闲位，避免堆分配。arm64 格式因 Top Byte Ignore 和扩展标签能力而调整，并使用进程随机值混淆。旧代码若硬编码某一位代表标签，升级后可能得出相反结论。

## 关键机制与结论

优化共同遵循“让常见对象只支付常见成本”：少变的类不分配扩展写时数据，方法用局部相对地址，微小对象免分配。Swift 类也共享部分 Objective-C Runtime 基础设施。最重要的工程结论不是记住结构图，而是通过 `class_getName`、`method_getImplementation`、类型检查等受支持入口访问语义。

演讲把内存账算得很具体：只读页可以由多个进程共享，也能在内存压力下从磁盘重新载入；被 Runtime 改写的脏页则是每个进程自己的常驻成本。因此，把冷门可变状态从每个类的固定结构中拆走，比单纯少几个字段更有系统级价值。

## 准确性 / 版本边界

演讲中的结构、位分布、系统级节省数字和部署目标行为是 iOS 14 / macOS 11 时代实现快照，不是公开 ABI。它们适合解释优化方向，不适合写进依赖布局的业务代码。提高最低部署版本可能让工具链采用更紧凑表示，但具体收益需以当前编译器和目标系统测量。
