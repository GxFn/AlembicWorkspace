# 用最小实现看懂引用计数

- **Original title**: Friday Q&A 2011-09-16: Let's Build Reference Counting
- **原文链接**: [原文](https://www.mikeash.com/pyblog/friday-qa-2011-09-16-lets-build-reference-counting.html)
- **作者 / 机构**: Mike Ash
- **年份**: 2011
- **材料类型**: 内存管理实现实验
- **文档性质**: 忠实中文精读，不是原文全文翻译

## 文章要解决的问题

“`retain` 加一、`release` 减一、归零销毁”很容易背，却不容易看出并发、存储位置和最后一次释放的真实约束。原文用一个刻意简单的实现，把引用计数从抽象规则还原成可执行的数据结构和原子状态变化。

## 原文论证主线

实验给 `NSObject` 增加 `ma_retain` 和 `ma_release`，并用全局 `CFMutableDictionary` 把对象地址映射到计数。为节省表项，计数为 1 被表示为“字典中没有记录”：新对象天然从 1 开始，只有更高计数才进入旁路表。

递增和递减都必须在锁保护下完成读取—修改—写回，不能把几个步骤各自做成“线程安全”后就认为组合也是原子的。`ma_retain` 增加计数并返回 `self`；`ma_release` 减少计数，若新值为零，则在离开计数操作后调用 `dealloc`。压力测试验证多次持有需要同样次数的释放，并展示 retain 与 release 本身可以来自不同线程，但对象最后一次释放与其他访问之间仍需更高层同步。

文章还解释，当年的 `NSObject` 默认实现为何可能把额外计数放在对象外，而某些类会自行覆盖内存管理方法并使用内联存储：这是空间、速度和对象布局之间的取舍。

## 关键机制与结论

引用计数只回答“当前还有多少个有效所有权”，不证明某个裸指针仍可安全访问。计数操作线程安全也不等于对象业务状态线程安全，更不能挽救一边执行最后一次 release、另一边才准备 retain 的竞态。循环引用的问题同样不会因计数表实现得更快而消失。

最后一次释放还暴露出可重入性：销毁对象可能继续释放它持有的其他对象，甚至触发任意清理逻辑。若仍拿着全局计数锁执行 `dealloc`，很容易再次进入计数路径而死锁，所以“判定归零”和“真正销毁”必须有清楚的锁边界。

## 准确性 / 版本边界

这不是可用于产品的替代实现。原文评论中 Chris Lattner 明确指出，它不兼容 ARC 的 zeroing weak，并绕开 Runtime 优化。文中的 `OSSpinLock` 后来被判定可能产生优先级反转，现代代码也不应照用。当前 Runtime 广泛利用 non-pointer `isa`、inline extra retain count 和 side table，早期“默认全在外部字典”不能视为现状。文章价值在状态机，不在数据结构。

## 在知识体系中的位置

这是 ARC 之前的拆机篇。它帮助理解 ARC 最终仍要落到所有权操作，也为 weak side table、non-pointer `isa` 和并发生命周期问题提供直觉。
