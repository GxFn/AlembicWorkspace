## 文章要解决的问题

很多开发者把 Dispatch Queue 想成“一条队列对应一条线程”。原文通过 Objective-C 重建最小队列，说明队列负责排序和同步语义，真正执行任务的是共享线程池；串行、并发、同步和异步可以由少量状态组合出来。

## 原文论证主线

底层先实现全局线程池。池维护待执行 Block、线程总数、忙碌线程数和固定上限，并用 `NSCondition` 同时承担互斥与等待/唤醒。Worker 在任务为空时用 `while` 重新检查条件，以应对虚假唤醒；取出任务并更新计数后必须先释放锁再运行 Block，否则所有工作都会被锁串行化，甚至形成死锁。

上层队列维护自己的待处理 Block、串行/并发标记，以及串行队列是否已有任务在飞。并发队列可以持续把任务交给线程池；串行队列一次只投递一个，当前任务完成后再触发下一个，从而保证顺序而不绑定固定线程。异步调用只入队后返回；教学版同步调用把任务包装为“执行后设置 done 并 signal”，调用线程则在条件变量上循环等待完成。

由此文章区分两种约束：线程池决定有多少 Worker 可以同时跑，队列决定哪些任务允许同时跑及调用者是否等待。多个队列共享线程池，才避免每建一条队列就创建一条线程。

## 关键机制与结论

串行描述的是同一队列中任务不重叠，不保证固定 OS 线程；异步描述提交者是否等待，不等于任务必然并行。锁只保护队列状态，业务 Block 应在锁外执行。同步等待依赖正确的完成信号，因此在同一串行执行上下文中自我同步提交会造成无法推进的等待。

## 准确性 / 版本边界

作者明确省略了 GCD 的自适应线程数、CPU/阻塞感知、QoS、Target Queue、Barrier 等能力，并使用任意固定线程上限和 Foundation 容器；性能远不及 libdispatch。现代 GCD、Swift Concurrency 的执行器和调度策略更复杂，不能据此推导“一任务一线程”或具体线程数量。本文实现用于揭示分层，不用于替代系统队列。
