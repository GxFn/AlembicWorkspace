## 文章要解决的问题

文章不是展示一张理想架构图，而是解释一个由数千名工程师维护、服务海量用户的混合代码库为何逐步偏离典型 iOS 工程。每一次自研框架、动态库、代码生成和语言边界，都是为了解决当时的可靠性、启动时间或协作规模问题，同时制造新的成本。

## 原文论证主线

2014 年，News Feed 的可变 Core Data 模型、双向数据流和多线程组合导致难以复现的问题，团队借鉴 React 建立单向数据流、不可变模型和声明式 ComponentKit，并获得明显性能改善；代价是新人必须学习平台之外的基础设施。

功能与贡献者增长后，pre-main 和各模块争抢启动入口逐渐失控。2016 年团队把大量产品代码放入延迟加载的 dylib，遏制启动成本增长，却打破了依赖“进程里所有类都已加载”的 Runtime 注册方式，也让错误常在运行时才暴露。随后 Buck 的依赖图被用来生成函数/类到 dylib 的映射，并发展成构建期插件系统，把“缺插件、重复插件、启动路径误加载 dylib”等失败前移到编译阶段。

代码生成减少了手工注册和合并冲突，却增加了间接层、陌生工具和调试难度。到 2020 年，Swift-only 平台 API 与开发者效率迫使团队重新划分语言边界：底层仍可保留 C++/Objective-C++ 实现，但面向产品的 API 尽量避免把 C++ 暴露出去，让 Swift 能成为正常参与者。结尾又反思，随着硬件和 Apple SDK 进步，一些历史优化应重新评估，能回归平台惯例时不必永久保留自研层。

## 关键机制与结论

架构是约束随时间累积的结果，不是模式竞赛。最有迁移价值的原则包括：让失败尽早发生；把依赖关系变成可查询图；区分底层实现语言与产品 API；每项性能优化都记录开发体验成本；平台能力改变后重新验证旧决策。Meta 的方案之所以成立，前提是它面对极端代码量、启动预算和组织并发。

## 准确性 / 版本边界

文中的规模、50% 改善、dylib 结构和 Buck 插件均属 Facebook 特定阶段，不能直接推广为普通 App 最佳实践。“C++ 还不能与 Swift 互操作”是 2023 年上下文，Swift 5.9 起已提供直接 C++ Interop，技术事实已变化；但隔离跨语言复杂度、维护稳定产品边界的理由仍成立。“几乎不用原生 SDK”也应读作成本陈述，而非模仿目标。
