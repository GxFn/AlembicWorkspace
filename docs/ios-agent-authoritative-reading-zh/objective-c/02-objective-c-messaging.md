## 文章要解决的问题

很多解释把 method、message、selector 和 message send 混用，随后又用一句“编译成 `objc_msgSend`”草草结束。原文先澄清术语，再追踪一条普通消息从源代码、编译器到 Runtime 方法缓存和实际函数实现的完整路径。

## 原文论证主线

method 是与类关联的一段实现代码；message 是发送给某个对象的名称和参数；selector 是对这个名称的 Runtime 表示；message send 则是根据接收者和 selector 找到并执行实现的过程。Objective-C 方法在机器层面可理解为普通 C 函数，只是多了隐式的 `self` 和 `_cmd` 参数。

编译器看到 `[obj foo:value]` 后，需要按该方法真实的参数和返回值约定生成调用。动态派发并不意味着编译器可以不知道类型；如果声明缺失或同名方法签名冲突，调用约定可能不匹配，结果不是“晚点再检查”，而是可能直接产生错误行为。

Runtime 先根据接收者获得类，再用 selector 查询方法缓存。命中时直接取得 IMP；未命中才沿类和父类的方法信息执行较慢查找，并把结果写入缓存供后续调用使用。IMP 是最终执行的函数地址，消息系统的价值正在于调用点无需预先绑定某个具体实现。

## 关键机制与结论

动态派发的动态部分是“运行时根据接收者实际类型选择 IMP”，不是“程序运行时才理解所有参数类型”。缓存让常见消息发送无需每次遍历继承链。selector 标识方法名称，Method 还携带类型编码和 IMP，三者不能互相替代。向 `super` 发送消息时接收者仍是当前 `self`，只是查找起点改变，也应放进同一个模型理解。

## 准确性 / 版本边界

原文展示的是早期、现已不透明的 `objc_class` 和缓存结构，循环次数及 x86 性能数字不能用作现代实现结论，也不能照着字段访问。普通 Objective-C 调用通常保留动态派发语义，但 `objc_direct`、编译器/链接器优化和消息发送 Stub 说明“所有方法调用都原样经过同一个 `objc_msgSend`”过于绝对。稳定结论是接收者、selector、查找语义和 IMP 之间的关系。

## 在知识体系中的位置

这是消息派发主干。它连接类/元类、消息转发、Swizzling、KVO 动态子类以及崩溃分析，也能把“调用目标究竟在编译、链接还是运行阶段确定”说到具体机制，而不使用含混的时间描述。
