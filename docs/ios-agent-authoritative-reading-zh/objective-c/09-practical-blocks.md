## 文章要解决的问题

文章写在 Blocks 尚未正式随 Apple 工具链发布的时期，目标不只是介绍 `^{}` 语法，而是说明闭包为何能替代大量回调样板、如何携带创建现场的上下文，以及这种便利会带来哪些生命周期和可读性风险。

## 原文论证主线

Block 被描述为 Objective-C 对象，同时保存可执行代码和创建时捕获的外部环境。普通局部变量按值捕获，默认不能在 Block 内修改；`__block` 提供可共享修改的存储语义。早期实现先在栈上构造 Block，若要返回、异步保存或跨出创建作用域，就必须复制到更长生命周期的存储。

原文通过一系列 API 设计展示闭包的意义：把锁定—执行—解锁包装为控制结构，把“延时执行”所需状态直接捕获，把集合映射和筛选写成传入行为，把 Delegate 风格的异步接口收束为完成回调。作者还提出一个可读性原则：当 Block 是主要工作体时，应让 Block 参数位于调用末尾，避免嵌套后必须倒着阅读控制意图。

最后转向风险。复制的 Block 会拥有捕获的 Objective-C 对象，直接或通过实例变量使用 `self` 都可能形成持有环；栈 Block 若未正确延长生命周期会悬空。闭包让上下文传递变容易，却不会自动给出正确所有权。

## 关键机制与结论

Block 是“代码 + 环境 + 调用入口”，不是特殊函数指针。是否逃逸决定生命周期要求，捕获关系决定对象图。设计回调时要同时回答：谁保存 Block、保存多久、Block 强持有哪些对象、取消时怎样断开关系。Blocks 后来成为 GCD 和大量 Cocoa 异步 API 的基础，正因为它能把操作和所需上下文放在一起。

## 准确性 / 版本边界

文章基于 Mac OS X 10.5、PLBlocks、MRC 和 GC，手工 `copy/release` 不是现代 ARC 写法。更重要的是，文中用 `__block` 对象引用规避持有环依赖当时的 MRC 语义；在 ARC 下 `__block` 默认并不等于弱引用，应使用明确的 `__weak` / `__strong` 策略。旧网络、集合和通知示例已有系统 API，保留的是闭包模型而非代码模板。

## 在知识体系中的位置

本篇连接 ARC、GCD、回调式异步和 Swift Closure。理解它后，再分析 Block ABI、逃逸、弱强舞步和队列捕获会更扎实。
