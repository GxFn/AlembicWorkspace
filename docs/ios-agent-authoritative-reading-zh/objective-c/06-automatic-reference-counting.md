# ARC 到底自动了什么

- **Original title**: Friday Q&A 2011-09-30: Automatic Reference Counting
- **原文链接**: [原文](https://www.mikeash.com/pyblog/friday-qa-2011-09-30-automatic-reference-counting.html)
- **作者 / 机构**: Mike Ash
- **年份**: 2011
- **材料类型**: 内存管理深度文章
- **文档性质**: 忠实中文精读，不是原文全文翻译

## 文章要解决的问题

ARC 发布时最常见的误解有两个：它是不是一种垃圾回收器，以及开启后程序员是否再也不用理解对象生命周期。原文把 ARC 放回 Objective-C 既有的所有权规则中，说明编译器能替人完成什么，又有哪些图结构问题只能由设计者解决。

## 原文论证主线

Clang 已经能用静态分析发现许多 `retain` / `release` 配对错误；ARC 的核心推进是让编译器直接依据同一套规则插入、移动或消除所有权操作。程序员不再手写大部分内存管理消息，但对象仍按引用计数释放，不存在追踪整个对象图的循环回收器。因此两个对象若以强引用互相持有，即使外界不再引用它们，也不会自动回收。

文章随后解释所有权限定符。强引用维持对象生命；弱引用不拥有对象，并在对象销毁后清零；`unsafe_unretained` 不拥有也不清零；某些间接参数需要 `autoreleasing` 语义。ARC 能和非 ARC 文件及库共存，使大型工程渐进迁移，而不是要求整个进程一次切换。

另一条主线是 Core Foundation 桥接。ARC 不能凭裸 C 指针语法自动知道所有权是否转移，所以需要区分“只改变类型视图”“把 CF 所有权交给 ARC”“从 ARC 取得并转交 CF 所有权”。这些桥接不是装饰性转换，而是在类型边界记录所有权变化。

## 关键机制与结论

ARC 是编译期所有权系统，Runtime 负责执行引用计数、弱引用和 autorelease 等底层操作。它能消除机械配对和优化多余操作，却不能替你设计无环的所有权图。Block 捕获 `self`、Delegate 方向、计时器和回调存储仍要判断谁应该拥有谁。判断 ARC 代码正确与否，应追踪强引用路径，而不是问某行“什么时候 release”。

## 准确性 / 版本边界

文章基于 Xcode 4.2 的首代 ARC，关于 Apple 垃圾回收、迁移工具、早期编译器缺陷和具体生成函数的细节已经历史化。现代编译器会做更多 retain/autorelease 配对消除，不能把示意展开当固定汇编。精确语言规则应以当前 Clang ARC 规范为准，但“编译器所有权、非循环回收、桥接显式转移”仍是稳定结论。

## 在知识体系中的位置

这是 Objective-C 内存管理主干。它应和手工构建引用计数、Autorelease Pool、Blocks 捕获以及 Swift 的 ARC/闭包循环并读，从语法记忆上升到所有权图分析。
