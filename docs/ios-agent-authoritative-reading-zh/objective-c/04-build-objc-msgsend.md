## 文章要解决的问题

“`objc_msgSend` 查到 IMP 再调用”仍遗漏了最难的一步：一个不知道后续参数和返回类型的中间函数，怎样不破坏 ABI，把原参数完整交给任意方法实现。原文通过重建一个能运行的简化版本，把消息发送器为何需要汇编以及为何称为 trampoline 讲具体。

## 原文论证主线

目标不是在 C 中写一个普通包装函数，因为 C 的可变参数调用约定不能透明转发所有正常参数。文章把工作拆成两层：x86-64 汇编入口保存可能承载参数的寄存器和必要状态，调用 C 函数查找 IMP，再恢复原参数并用跳转而非嵌套调用把控制权交给 IMP。这样目标方法返回时会直接回到最初调用者，返回值也自然留在 ABI 规定的位置。

C 层先取接收者的类，在方法缓存中按 selector 查找；未命中时交给 Runtime 的慢路径获得实现，后续调用便可受益于缓存。文章还说明大结构体或特殊浮点返回值为何在某些 ABI 上需要 `objc_msgSend_stret`、`objc_msgSend_fpret` 等变体：隐藏返回地址或特殊寄存器会改变 `self`、`_cmd` 所在位置。

## 关键机制与结论

消息发送器不是一个理解每个业务参数的通用反射函数，而是尽量不碰参数、只解析目标地址的极短跳板。高性能来自缓存命中、手写汇编和尾跳转。方法最终仍按正常 C ABI 接收 `self`、`_cmd` 与显式参数，因此直接调用 IMP 或手工转换 `objc_msgSend` 时，函数指针签名必须正确。

“透明”并不只意味着保住几个整数寄存器：实现还要遵守浮点与向量参数、栈对齐、可变参数、结构体返回和调用者保存规则。文章选择汇编，正是因为编译器生成的普通 C 函数序言可能先改动这些尚未被解释的调用现场。

## 准确性 / 版本边界

实验针对 2012 年 macOS x86-64，使用了当时的私有类和缓存布局，并简化或遗漏了 `nil`、并发缓存演进及部分寄存器情形。ARM64 的寄存器、返回规则和现代缓存完全不同，某些 `_stret` 分支也不适用于 ARM64。原文明确警告绝不能在产品中替换系统 `objc_msgSend`；它只能解释机制，不能当实现模板。

## 在知识体系中的位置

这是消息派发的进阶拆机篇。读完基础 Messaging 后再读它，可以把 selector、缓存、IMP、调用约定和汇编跳板连成真实调用链，也能理解为何错误签名常表现为随机寄存器或返回值损坏。
