# 不要默认构建多 Agent

- **Original title**：Don’t Build Multi-Agents
- **原文链接**：[Cognition 原文](https://cognition.com/blog/dont-build-multi-agents)
- **作者/机构**：Walden Yan；Cognition
- **年份**：2025
- **材料类型**：厂商工程立场 / 生产经验文章
- **文档性质**：忠实中文精读，不是原文全文翻译。

## 文章要解决的问题

并行子 Agent 看似能加速大型任务，但 Cognition 在长时编码 Agent 中观察到成品容易风格冲突、边界错位且难以合并。文章追问：即使给每个子任务清楚指令，为什么并行写入仍然脆弱？

## 原文论证主线

作者提出两条上下文工程原则。第一，相关上下文应共享，最好包括完整轨迹而非孤立消息，因为真实任务的意图、工具观察和决策分散在多轮历史中。第二，行动携带隐式决策：一次代码或设计修改同时选择了风格、结构和边界条件；并行执行者看不到彼此行动时，会作出相互冲突但单独看都合理的选择。把最终结果交给另一个 Agent 合并，并不能恢复已丢失的共同判断。

## 关键机制与结论

作者建议默认从单线程、连续上下文 Agent 开始。任务过长时，可用专门模型把行动与对话压缩为关键事件和决策；子 Agent 更适合只读、边界清楚的调查，完成后把信息返回主 Agent，而不是同时改写同一产品。文章并非证明任何并行都不可能，而是认为 2025 年模型还难以用足够低的损耗主动传递跨 Agent 上下文。

## 证据与适用边界

论据来自 Cognition/Devin 的工程观察、编码场景与具体反例，没有公开样本量、成功率或统一对照实验；“多 Agent 会脆弱”因此是强烈但有领域限制的生产判断。它发表后模型和产品迅速演进，作者在 2026 年续篇明确承认某些窄模式已经有效，所以不能把标题当作永久禁令。

## 在知识体系中的位置

这篇强调多 Agent 最大成本不只是 token，而是上下文与决策一致性。它与 Anthropic 的并行研究并不真正冲突：只读搜索可独立压缩信息，而多个写者会把隐式产品决策分散到无法可靠合并的轨迹中。

## 精读时应保留的判断

“共享全部上下文”与“给每个 Agent 干净窗口”看似矛盾，实则取决于职责。共同写作需要共享已作出的产品决策；独立审查则有意隔离原作者轨迹，再由拥有全局意图的主体筛选意见。不要让子 Agent 只拿一句摘要便改共享状态，也不要把整个历史无差别复制到每个分支。更稳妥的默认是只读调查、明确交付物、单一写入者，以及对跨 Agent 消息保留来源和未解决不确定性。
