# 长时间运行 Agent 的有效 Harness

- **Original title**：Effective harnesses for long-running agents
- **原文链接**：[Anthropic 原文](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- **作者/机构**：Justin Young 及 Anthropic Claude Code、Code RL 团队
- **年份**：2025
- **材料类型**：厂商实验复盘 / 运行控制方法
- **文档性质**：忠实中文精读，不是原文全文翻译。

## 文章要解决的问题

单次上下文结束后，新会话并不天然知道前一会话做过什么。仅靠自动压缩，长任务中的 Agent 容易一次做太多、留下半成品、重复摸索环境，或看到已有进度便过早宣布完成。文章研究 harness 如何让多次会话持续、可恢复地推进。

## 原文论证主线

作者把工作分成初始化会话和后续编码会话。初始化 Agent 建立启动脚本、完整功能清单、进度文件和初始提交；后续 Agent 每次先确认目录，读取日志、功能状态和 git 历史，启动应用并验证基础链路，再只选择一个未完成特性增量实现。结束前必须做端到端测试、更新进度并提交干净状态，为下一班“工程师”留下可审计交接物。

## 关键机制与结论

持久状态不藏在对话摘要中，而落在结构化需求、版本历史、可执行启动方式和验证结果里。功能清单初始全部为失败，并限制 Agent 只能更新通过状态，减少擅自删改需求；一次只推进一个特性，降低上下文耗尽时留下不一致状态的概率；每次先跑最小用户链路，若基线已坏就先修同一链路。Harness 的作用是塑造恢复、选择、验证和交接的纪律。

## 证据与适用边界

文章以 Claude Agent SDK、Opus 4.5 和构建 claude.ai 类全栈 Web 应用的内部实验为核心，观察浏览器端到端测试明显优于只看代码或 `curl`。它没有给出大样本基准、与多种 harness 的完整统计对照；浏览器自动化和视觉能力也有已知盲区。结论尤其适合软件工程，不能直接外推到科学研究或金融任务。

## 在知识体系中的位置

这篇把“记忆”转成运行控制：需求、工作状态、证据和恢复点分别落盘。它与 12-Factor Agents 一起说明，可靠长任务往往依赖普通软件工程原语，而不是让一个对话无限延长。

## 精读时应保留的判断

跨会话交接物必须能够独立核验，而不是只写“已完成大部分”。功能清单应连接真实验收步骤，进度记录应区分已验证事实、当前假设和下一步，提交记录只能证明改过代码，不能证明用户链路通过。新会话开始时先跑最小主链，是为了发现前一会话留下的断点；若主链失败，应在同一链修复，而不是继续扩展周边功能。该纪律也适用于非编码任务中的状态快照与证据包。
