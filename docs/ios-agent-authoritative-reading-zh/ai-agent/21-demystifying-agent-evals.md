# 拆解 AI Agent 评测

- **Original title**：Demystifying evals for AI agents
- **原文链接**：[Anthropic 原文](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- **作者/机构**：Anthropic
- **年份**：2026
- **材料类型**：厂商工程指南 / 评测方法总结
- **文档性质**：忠实中文精读，不是原文全文翻译。

## 文章要解决的问题

Agent 会在多轮中调用工具并改变环境，最终回复声称“已完成”不代表真实状态成功；同一任务重复运行还可能得出不同结果。文章建立任务、trial、grader、轨迹、结果状态和 harness 的共同词汇，并给出从零搭建评测的路线。

## 原文论证主线

评测应先定义可独立判定的任务与成功条件，再运行多次 trial，完整保存模型消息、工具调用、推理和中间结果。评分对象既可以是轨迹，也可以是最终环境状态；后者通常更接近用户结果。grader 分为确定性代码、模型评分和人工评审，各自承担客观检查、开放质量和校准。能力集用于寻找尚不会做的任务，回归集则保护已经稳定通过的能力。

## 关键机制与结论

文章强调组合评分：编码 Agent 用测试、静态分析和质量 rubric；会话 Agent 同时检查数据库状态、流程约束和交互质量；研究 Agent 检查事实依据、覆盖与来源质量。非确定性要通过多次运行表达：`pass@k` 关心多次中至少一次成功，`pass^k` 关心每次都成功，面向用户的稳定服务通常更应关注后者。早期可从 20—50 个真实失败与手工检查起步，并持续把生产问题沉淀为回归任务。

## 证据与适用边界

建议来自 Anthropic 内部及 Descript、Bolt 等客户实践，并引用 SWE-bench、Terminal-Bench、τ-bench、WebArena、OSWorld 等示例；它不是一项统一对照实验。模型 grader 会漂移且需要专家校准，模拟用户不等于真实用户，静态任务库还可能被过拟合。文章自身也展示 frontier Agent 有时利用政策漏洞得到对用户更好的答案，说明 grader 可能错而非 Agent 错。

## 在知识体系中的位置

这是从抽象“要做 eval”走向可执行评测体系的主文。它把最终状态、多次试验、成本延迟和完整轨迹统一起来，也是理解 τ-bench、AgentRx 与生产可观测性的前置材料。

## 精读时应保留的判断

任务库质量比任务数量更重要。每条任务应让两名领域专家在不猜意图的情况下判断通过或失败，并包含初始状态、允许动作、预期状态与重要非目标。最终状态正确也不代表过程安全，例如 Agent 可能先泄露数据再完成退款，因此结果 grader 与轨迹约束要并用。`pass^k` 会随 k 快速下降，选择 k 应对应真实用户重复使用的可靠性要求，而不是为了制造好看或难看的数字。
