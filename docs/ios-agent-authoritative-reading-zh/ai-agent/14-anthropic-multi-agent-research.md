# Anthropic 多 Agent 研究系统复盘

- **Original title**：How we built our multi-agent research system
- **原文链接**：[Anthropic 原文](https://www.anthropic.com/engineering/multi-agent-research-system)
- **作者/机构**：Anthropic Research 产品与工程团队
- **年份**：2025
- **材料类型**：厂商生产复盘
- **文档性质**：忠实中文精读，不是原文全文翻译。

## 文章要解决的问题

开放式研究无法预先写死搜索路径，且信息量可能超过单个上下文。文章说明 Anthropic 为什么在 Research 产品中采用“主 Agent + 并行子 Agent”，这种架构在哪些任务上有效，以及协调、成本和评测会遇到什么问题。

## 原文论证主线

系统使用 orchestrator-worker：主研究 Agent 分析问题、保存计划、给子 Agent 分配互不重复且边界明确的方向；子 Agent 独立搜索、根据发现迭代，再压缩结果返回；主 Agent 综合后决定是否继续；末尾由引用 Agent 把结论定位到来源。作者把搜索描述为压缩问题：子上下文并行消化大量材料，主上下文只接收高密度发现。

## 关键机制与结论

有效委派需要目标、输出格式、工具和来源要求、任务边界，而不是一句模糊主题。主 Agent 还需控制子 Agent 数量、token 预算、停止条件与结果质量。多 Agent 最适合高价值、可并行、信息超过单窗口且工具复杂的任务；依赖强、需要所有执行者共享同一状态的工作并不合适。它获得的能力很大部分来自允许系统使用更多推理与搜索预算。

## 证据与适用边界

Anthropic 报告内部研究评测中，Opus 4 主 Agent + Sonnet 4 子 Agent 相比单个 Opus 4 提升 90.2%；对 BrowseComp 的分析中，token 用量解释约 80% 表现方差。代价是 Agent 约用聊天的 4 倍 token，多 Agent 约为聊天的 15 倍。评测集、生产流量和完整配置未公开，数字不能外推到编码或低价值任务；作者也明确说许多编码任务缺少真正并行性。

## 在知识体系中的位置

这是一份有边界的正面案例：它证明多 Agent 可为“广度优先研究”扩展上下文和搜索，但同时提供成本与不适用条件。应与 Cognition 的反例和 Google 的受控实验一起阅读。

## 精读时应保留的判断

采用该架构前应先证明子问题彼此独立，且汇总者能验证返回结果，而不是仅因任务“很大”就并行。委派包至少包含原始目标、该分支范围、禁止越界事项、期望证据和输出格式；主 Agent 还要检查遗漏、重复、来源冲突与停止条件。90.2% 提升不能与 15 倍 token 成本分开阅读，真正决策指标应是单位成本、单位时间的可验证任务价值，以及错误能否被汇总层发现。
