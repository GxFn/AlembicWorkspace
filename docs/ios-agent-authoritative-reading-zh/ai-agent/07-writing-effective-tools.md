# 为 AI Agent 编写有效工具

- **Original title**：Writing effective tools for agents — with agents
- **原文链接**：[Anthropic 原文](https://www.anthropic.com/engineering/writing-tools-for-agents)
- **作者/机构**：Ken Aizawa 及 Anthropic Research、MCP、产品工程团队
- **年份**：2025
- **材料类型**：厂商工程复盘 / 工具设计方法
- **文档性质**：忠实中文精读，不是原文全文翻译。

## 文章要解决的问题

传统 API 面向确定性调用者，而 Agent 会误选工具、填错参数、忽略结果或走低效路径。文章研究的不是“如何声明函数”，而是如何设计一种让概率性调用者更容易理解、组合和纠错的软硬件契约。

## 原文论证主线

作者提出评测驱动的迭代：先做能运行的原型，以真实多步任务建立带可验证结果的评测，记录轨迹、工具调用、耗时、token 和错误，再从轨迹中修改工具。总结出的设计原则包括：只实现高价值且边界清楚的工具；合并经常连续发生的底层操作；用命名空间消除重叠；返回语义明确、与下一步有关的信息；提供过滤、分页与精简/详细模式；用清晰描述、数据模型和可操作错误帮助 Agent 修正调用。

## 关键机制与结论

工具不是把每个后端 endpoint 原样暴露。`search_logs` 往往比返回全部日志的 `list_logs` 更适合上下文有限的模型；面向业务的 `schedule_event` 也可能比三个低层 API 更稳定。工具返回值既是程序输出，也是下一轮模型上下文，因此字段名、标识符、格式和 token 体积都会影响决策。真正的接口质量需由端到端任务成功率证明，而非由人类觉得“API 很优雅”证明。

## 证据与适用边界

Anthropic 用内部 Slack、Asana 等工具的训练集与留出集持续优化，并报告 Agent 优化后的工具可超过人工“专家”版本；文章展示若干性能图和 token 对比，但没有公开完整数据、任务集与所有模型配置，无法复现为普遍增益。命名前后缀、JSON 或 Markdown 的最优选择也被明确说明会随模型和任务变化。

## 在知识体系中的位置

这是从 ReAct 抽象循环走向生产实现的关键一篇。它说明很多看似“模型不会用工具”的问题其实属于 Agent—计算机接口设计，并把工具、上下文预算、评测和可观测轨迹连接起来。

## 精读时应保留的判断

审查一个工具时，可依次问：名称能否与相邻工具区分，输入是否能被严格校验，默认值是否安全，返回值是否足以支持下一步，错误是否告诉 Agent 如何恢复，写操作是否显露影响范围与可逆性。不要把“调用成功”当任务成功；还要检查 Agent 是否选对对象、后台状态是否正确。工具合并也有边界：过度聚合会把关键授权和可观测步骤藏到黑箱内部，需在易用性与控制力之间评测。
