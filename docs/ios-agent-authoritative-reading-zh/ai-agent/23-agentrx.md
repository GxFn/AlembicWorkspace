# AgentRx：从执行轨迹系统定位 Agent 失败

- **Original title**：Systematic debugging for AI agents: Introducing the AgentRx framework
- **原文链接**：[Microsoft Research 原文](https://www.microsoft.com/en-us/research/blog/systematic-debugging-for-ai-agents-introducing-the-agentrx-framework/)

- **年份**：2026
- **材料类型**：研究框架发布 / 论文与开源数据解读
- **文档性质**：忠实中文精读，不是原文全文翻译。

## 文章要解决的问题

长轨迹往往包含多个错误，最后一步失败不一定是根因；多 Agent 还会把上游错误包装后继续传递。AgentRx 要定位的是第一个使任务不可恢复的“关键失败步骤”，并用可审计证据解释原因。

## 原文论证主线

框架先把不同系统的轨迹归一成共同表示，再根据工具 schema 和领域政策自动合成可执行约束，例如返回值必须满足结构、删除前必须获确认。每条约束带 guard，只在适用步骤检查，形成逐步违规日志。最后由 LLM judge 结合日志与九类失败 taxonomy，判断关键步骤和根因类别，而不是直接对几十步原始文本凭感觉作答。

## 关键机制与结论

九类根因包括计划遵循、凭空发明、无效调用、误读工具输出、意图—计划错位、用户意图不足、能力不支持、护栏触发和系统故障。方法把确定性的 schema/政策检查放在前面，把开放判断限制在已有证据之后。其工程价值是从“任务失败了”推进到“从哪一步起已无法恢复、违反了哪条可执行约束”。

## 证据与适用边界

AgentRx Benchmark 含 115 条人工标注失败轨迹，来自 τ-bench、Flash 事件处置和 Magentic-One 开放任务。相对提示基线，失败定位准确率绝对提高 23.6%，根因归类提高 22.9%。样本只包含失败轨迹且规模有限；自动合成的约束可能不完整，最终仍依赖 LLM judge，所以它不是形式验证，也不能保证找到所有隐性业务错误。

## 在知识体系中的位置

这是可观测性与调试的核心材料：完整轨迹只是原料，真正有用的是定位第一个不可恢复错误并关联工具契约与政策。它补足 τ-bench 的“是否成功”，回答“为什么失败、先修哪里”。

## 精读时应保留的判断

定位第一个“出现异常”的步骤与第一个“不可恢复”的步骤并不总相同：Agent 可能在后续通过查询或回滚修正早期误判。因此约束需要表达恢复条件，而不是见到一次错误码就判死。日志还应记录工具版本、环境状态和政策版本，才能重放当时判断。AgentRx 的 taxonomy 可作起点，但业务团队要从自己的失败轨迹扩充类别；调试结论最终应指向可修复的模型、提示、工具、数据或环境责任层。
