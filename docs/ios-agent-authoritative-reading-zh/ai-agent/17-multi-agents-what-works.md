## 文章要解决的问题

在《Don’t Build Multi-Agents》十个月后，模型更擅长工具、上下文压缩和委派，Cognition 也积累了更多生产使用。续篇重新划界：哪些多 Agent 组合开始产生真实收益，哪些“群体自治”仍只是演示。

## 原文论证主线

文章分析三个方向。其一，编码 Agent 与干净上下文的审查 Agent 循环，审查者只从 diff 和代码重新发现事实，再由主 Agent 根据完整用户意图筛选意见。其二，较小主模型把困难问题交给“smart friend”大模型，但弱模型是否知道何时升级成为瓶颈；强模型之间按能力路由更可行。其三，管理者 Agent 拆分更大范围，子 Agent 执行，管理者综合，但需要专门解决状态假设和跨子任务通信。

## 关键机制与结论

贯穿全文的经验是“一个写者，多个智能贡献者”。额外 Agent 用独立上下文做审查、咨询或只读探索，最终写入和产品判断仍由单线程主体负责。干净上下文能避开长轨迹的注意力稀释，但必须有桥梁把审查结果放回完整意图中。作者仍不看好任意 Agent 自由协商的 swarm，倾向 map-reduce-and-manage 的层级结构。

## 证据与适用边界

文中称 Devin Review 在 Devin 编写的 PR 上平均发现约 2 个缺陷，约 58% 被归为严重；还报告 Claude 与 GPT 的强模型组合在困难场景有收益，但没有公开样本分布、基线、置信区间和成本明细。弱主模型 + 强顾问的实验并未达到预期。所有证据主要来自软件工程产品，不能直接外推到客服、研究或高风险自动执行。

## 在知识体系中的位置

这篇最有价值之处是公开修正旧立场，并给出更细的设计变量：是否共享上下文、谁写入、谁拥有最终判断、通信如何回到全局意图。应与前篇并读，而不是只选一个标题站队。

## 精读时应保留的判断

生成—审查循环要避免两种假象：审查者提出很多问题不等于质量提升，主 Agent 全部照单修改也不等于协作成功。应跟踪真实缺陷被发现和修复的比例、误报、循环次数、额外成本及是否引入回归。Smart Friend 还要求主模型能识别能力边界；若它不会升级或不会带齐证据，强模型也无法补救。任何管理者—子 Agent 结构都需显式声明状态并不自动共享，重要发现要有确定的回传与广播路径。
