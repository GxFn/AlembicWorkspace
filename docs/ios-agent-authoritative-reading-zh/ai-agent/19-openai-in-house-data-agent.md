# OpenAI 内部数据 Agent 的构建复盘

- **Original title**：Inside OpenAI’s in-house data agent
- **原文链接**：[OpenAI 原文](https://openai.com/index/inside-our-in-house-data-agent/)
- **作者/机构**：Bonnie Xu、Aravind Suresh、Emma Tang；OpenAI
- **年份**：2026
- **材料类型**：厂商生产复盘
- **文档性质**：忠实中文精读，不是原文全文翻译。

## 文章要解决的问题

在 600 PB、7 万个数据集和 3500 多名内部用户的环境中，分析难点不只是生成 SQL，而是选对表、理解派生逻辑、遵守权限并验证结果。文章说明一个数据 Agent 如何围绕组织上下文而非单一“SQL 模型”构建。

## 原文论证主线

系统以六层上下文支撑 Agent：表使用与 lineage、专家人工注释、Codex 从生产代码推导的表语义、Slack/Docs/Notion 中的机构知识、可由用户确认和编辑的记忆、以及查询时直接检查仓库与数据平台的运行时上下文。离线管道归一化并嵌入部分资料，运行时只检索相关内容；Agent 根据中间结果自查、改查询，并在 Slack、Web、IDE、CLI 等入口继续对话。

## 关键机制与结论

文章强调“意义存在于生成数据的代码中”：schema 和历史 SQL 只显示形状与惯用法，pipeline 才包含过滤、更新频率和业务假设。质量控制用人工编写的黄金 SQL，执行 Agent SQL 与黄金 SQL，并同时比较语句和结果集，不依赖字符串完全一致。权限采用 pass-through，用户只能访问原本获准的数据；回答附上假设、执行摘要和底层结果链接供复核。工具则从重叠全集收缩为边界更清楚的集合。

## 证据与适用边界

文章给出真实规模、架构和失败模式，却未公开成功率、生产错误率、评测集、人工节省时间的分布或安全事件，因此不能证明该设计在其他公司同样有效。OpenAI 拥有特殊的数据平台、代码可访问性、内部身份系统和模型能力；“完整上下文跨轮保留”也不等于无损永久记忆。它是单组织案例，不是数据 Agent 通用基准。

## 在知识体系中的位置

这是把复合系统、上下文、记忆、工具、权限和持续评测连成一条生产链的代表案例。它特别适合说明：领域 Agent 的壁垒常在高质量语义层与验证闭环，而不只是调用哪个模型。

## 精读时应保留的判断

数据 Agent 的正确性至少分三层：选对数据语义、写出正确变换、把结果解释成正确业务结论。黄金 SQL 与结果集主要覆盖前两层，最终叙事仍需领域判断。记忆写入应由用户确认并可编辑，避免一次错误分析固化为组织知识。权限继承也只解决“能否读取”，不解决查询是否合目的、聚合后是否形成敏感信息。复用此案例时，应先盘点本组织是否拥有可追溯代码、元数据和权威指标定义。
