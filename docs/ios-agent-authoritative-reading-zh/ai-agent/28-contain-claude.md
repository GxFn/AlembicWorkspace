# Anthropic 如何在不同产品中约束 Claude

- **Original title**：How we contain Claude across products
- **原文链接**：[Anthropic 原文](https://www.anthropic.com/engineering/how-we-contain-claude)
- **作者/机构**：Max McGuinness、Mikaela Grace、Jiri De Jonghe、Jake Eaton、Abel Ribbink；Anthropic
- **年份**：2026
- **材料类型**：厂商安全工程复盘
- **文档性质**：忠实中文精读，不是原文全文翻译。

## 文章要解决的问题

模型能力与权限提高后，失败概率即使下降，单次错误可造成的爆炸半径仍会上升。文章不把“让模型更听话”当作唯一答案，而是比较 claude.ai、Claude Code 和 Cowork 如何按用户能力与产品环境设置不可由模型绕过的边界。

## 原文论证主线

风险分为用户误用、模型误行为和外部攻击；防御分为运行环境、模型层和外部内容三部分。claude.ai 代码在服务端临时 gVisor 容器中运行；Claude Code 在开发者本机用 macOS Seatbelt/Linux bubblewrap 限定工作区写入并默认禁网，同时保留人工监督；面向非技术用户的 Cowork 用本地 VM、挂载目录和细粒度读写模式，把凭据留在宿主机并限制出站。

## 关键机制与结论

文章的核心是先限制“能做什么”，再优化“倾向做什么”。模型提示和分类器是概率性层，沙箱、文件边界、短期凭证和出站代理才是硬边界。真实教训包括：信任确认前解析项目配置导致漏洞；钓鱼让用户亲自传入恶意指令时，意图分类无法识别；只按域名放行出站仍可借获准 API 向攻击者账户上传；VM 隔离也会挡住企业 EDR 的可见性。

## 证据与适用边界

内部遥测显示用户约批准 93% 的权限提示，沙箱上线后提示量降低 84%；一次内部钓鱼测试中，Claude Code 在 25 次尝试里 24 次按恶意用户提示外传凭据。文中还有公开披露和产品事故，但这些数字属于 Anthropic 的用户群、模型和产品配置，不可当作其他 Agent 的基线。安全细节也会随版本改变，且厂商自述不替代独立审计。

## 在知识体系中的位置

这是本资料安全部分的落地终点：AgentDojo 测注入，CaMeL 约束控制/数据流，OWASP 与微软提供 taxonomy，而本文展示成熟容器、VM、文件和网络原语怎样实际限制损害。最重要的结论是，任何概率性模型防线都不应独自承担权限边界。

## 精读时应保留的判断

Containment 设计应从最坏情况下 Agent 已被完全说服出发，检查它仍能读取、写入、联网和持有哪些凭据。域名 allowlist 不是能力 allowlist，同一域名可能暴露上传、转发或跨账户接口；文件路径校验也必须先解析符号链接。隔离强度要与用户判断能力匹配，但任何审批都需控制频率，避免疲劳。还要提前解决安全与可观测性的冲突：VM 挡住攻击的同时也可能挡住 EDR，因此审计通道必须单独设计。
