# TODO Submode And Window Scheduling Policy

状态：长期流程规则
维护窗口：AlembicWorkspace

本文规定总控处理 TODO 子模式和空闲窗口调度的方式。TODO 不是只用于修复问题，它是需求设计、代码调研、目标阶段确认、wave 派发、监控、验收和真实测试之间的轻量滚动清单。

用户可以在任何阶段要求新增、调整、取消或重排 TODO。总控必须把最新 TODO 落到当前正确文档位置，并用它影响下一轮需求设计、目标阶段确认、执行计划或窗口派发；不得只在最终回复里口头记录。

## 触发条件

只要出现以下任一情况，当前 workspace 总控文档必须新增或更新 TODO：

- 用户在需求讨论中提出待补充点、偏好、风险、验证点、设计候选或后续优化项。
- 用户明确要求调整 TODO 列表、重排优先级、把某项转入下一轮或暂缓。
- 用户明确反馈一组问题、多个优化点或希望后续统一修复。
- 真实项目验证暴露多个问题，且其中一部分阻塞主线、一部分可并行。
- 总控验收发现下游还不能继续，需要先修复上游，同时仍有其它窗口可做独立补齐。
- 当前 wave 之外出现新的问题，但不应打断已经执行中的窗口。

如果 TODO 仍处于需求设计或代码调研阶段，写入对应 `docs/requirement-designs/<需求名>/requirement-design-YYYY-MM-DD.md`。如果 TODO 已经影响目标阶段确认、wave 派发或下一波执行顺序，写入当前 `docs/workspace/` 总控文档，并同步维护 `空闲窗口调度`。

## TODO / Backlog

TODO 列表必须写进当前总控文档，而不是只写在最终回复里。推荐字段：

| ID | 状态 | 类型 | 严重度 / 优先级 | 归属 | 事项 / TODO | 影响复测 / 派发 | 依赖 / 触发 | 推荐窗口 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| TODO-1 | 主线 | 需求 / 设计 / 风险 / 修复 / 验证 / 文档 / 清理 | P0 / P1 / P2 | `Repo` |  | 是 / 否 |  | `Repo` |

状态建议使用：

- `主线`：当前必须优先处理，通常阻塞真实复测或后续派发。
- `可并行`：与主线无文件冲突、无上游依赖，空闲窗口可执行。
- `阻塞`：等待上游提交、用户确认、外部权限或真实运行条件。
- `观察`：当前不派发，但上游结果可能触发任务。
- `执行中`：窗口已经领取并正在处理。
- `待验收`：窗口已回填，等待总控验收。
- `已完成`：总控验收通过，有提交和验证证据。
- `取消/不做`：确认不做，并写明理由。

每个 TODO 至少要写清：

- 类型：需求、设计、风险、修复、验证、文档、清理、发布或其它。
- 事项现象、用户反馈或目标。
- 归属仓库和推荐执行窗口。
- 是否影响真实复测、目标阶段确认、窗口派发或下一波顺序。
- 依赖关系和触发条件。
- 验收或完成定义的关键证据。

## 需求设计期 TODO

需求设计期 TODO 是设计输入，不是执行派发。它用于记录：

- 用户还在讨论中的偏好、限制或完成定义。
- 需要代码调研验证的假设。
- 可能影响阶段顺序的风险。
- 需要后续拆成 wave 的候选事项。
- 真实测试前必须准备的验证点。

需求设计期 TODO 不能绕过原始计划书确认、需求设计、代码实现依赖调研和任务级目标阶段确认。只有当它被总控归入目标阶段确认或 wave 执行计划后，才能进入窗口派发。

## 空闲窗口调度

当 TODO 已经影响目标阶段确认、wave 派发或下一波执行顺序时，必须在当前 `docs/workspace/` 总控文档中维护空闲窗口调度。推荐字段：

| 窗口 | 当前调度 | 理由 | 是否发送 |
| --- | --- | --- | --- |
| `Repo` | 主线 / 可并行 / 阻塞 / 观察 / 无任务 / 已完成 |  | 是 / 否 |

空闲窗口可以并行派发，必须同时满足：

- 没有等待中的上游 contract、API、artifact、提交或用户确认。
- 不与主线修改同一批文件或同一模块边界。
- 能独立完成、独立验证、独立回填。
- 对需求设计、真实复测、稳定性、可观测性、发布链路或后续验收有实际价值。
- 当前总控文档已经写清目标、范围、禁止事项、验证命令、文档动作和回填位置。
- 当前总控文档和提示词已经要求执行窗口读取目标仓库 `AGENTS.md`，并先明确当前窗口定位 / 仓库职责。

以下情况不得为了“利用空闲窗口”而派发：

- 窗口只能观察，不能产生有效代码或验证证据。
- 下游需要猜上游字段、复制临时 contract 或提前做 fallback。
- 任务只是整理、抽象、空 adapter、无消费方 glue code。
- 发送后只能空跑、重复验证、或等待同一个阻塞条件。

## TODO 组包派发

TODO 进入派发阶段后，总控默认应按任务包派发，而不是逐条拆成零散小工单。任务包的目标是减少窗口来回切换，并确保当前真实阻塞点之前的主线动作尽量一波完成。

组包前必须先回答：

- 当前阶段目标是什么？
- 下一处真实阻塞点是什么？
- 阻塞点之前还能安全完成哪些主线动作？
- 哪些 TODO 与当前主线动作属于同一窗口、同一边界、同一验证链路？
- 哪些 TODO 因上游依赖、文件冲突、职责边界不同或验证路径不同，必须留到后续包？

推荐任务包字段：

| 任务包 ID | 窗口 | 阶段目标 | 主线动作 | 合并 TODO | 明确不包含 | 执行前置硬规则 | 阻塞 / 依赖 | 验证命令 | 回填要求 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| PKG-1 | `Repo` |  |  | `TODO-ID` / 无 |  | 读取目标仓库 `AGENTS.md`，明确当前窗口定位 / 仓库职责 |  |  |  |

组包规则：

- 先保证主线闭环，再合并同窗口可关闭 TODO，再安排独立并行项。
- 如果当前阻塞点之前还有同阶段可推进事项，应合入当前包；不要只派最小一小步。
- 不要为了“显得充分”硬塞无关 TODO；模糊完成定义的 TODO 必须独立或后置。
- 若当前只能派发一个小任务，必须在总控文档或回复中说明原因。
- 任何可发送任务包都必须把 `AGENTS.md` 读取和窗口定位声明写成执行前置硬规则；如果无法定位当前仓库，执行窗口应停下回填阻塞。

## 验收与滚动

每次需求设计更新、目标阶段确认、wave 验收或下一波派发前都要同步更新 TODO：

- 已修复的 TODO 标为 `已完成`，写提交 hash、验证命令和结果。
- 未完成但仍有效的 TODO 移到下一波，重新判断主线 / 可并行 / 阻塞。
- 发现新问题时新增 TODO，不要埋在验收说明里。
- 如果某个 TODO 被证明不需要做，标为 `取消/不做` 并写理由。
- 如果用户调整 TODO 优先级或范围，必须重算窗口状态、执行顺序和发送名单。

## 脚本检查

当当前计划使用 TODO 子模式来影响派发、并行调度或下一波顺序时，总控应运行：

```text
node scripts/check-todo-board.mjs --require
```

该脚本检查当前总控计划是否包含 `TODO / Backlog` 和 `空闲窗口调度` 章节，并做基础格式检查。它不替代总控判断，只防止 TODO 队列和空闲窗口调度缺失。

当当前计划使用任务包派发，或下一波分派需要把主线动作与 TODO 合并派发时，还应运行：

```text
node scripts/check-task-packages.mjs --require
```

该脚本只检查任务包章节和字段是否存在，不替代总控对阻塞点、边界和验证路径的判断。
