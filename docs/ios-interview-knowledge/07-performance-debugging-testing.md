# 质量、性能与诊断：用证据闭环

> 知识树定位：F1 测试、F2 性能、F3 稳定性、F4 工具、F5 线上可观测性；所有 A～E 的结论都应在 F 中得到验证。

## 1. 顶层闭环

```text
定义用户问题与成功指标
→ 在可控环境复现
→ 收集黑盒和白盒证据
→ 建立可证伪假设
→ 在真正热点修复
→ 同场景回归
→ 灰度和线上监控
```

反模式：

- 没有基线就“优化”；
- 看到某个方法耗时就立即重写；
- 只测 Debug/模拟器；
- 修复后只看一次平均值；
- 用测试通过证明用户体验一定正确；
- 用线上指标相关性直接断言根因。

## 2. 指标分类

| 质量维度 | 用户问题 | 代表指标 |
| --- | --- | --- |
| 正确性 | 结果是否符合需求 | 测试、业务一致性、错误率 |
| 启动 | 多久可见、可交互 | launch phases、首屏时延 |
| 响应 | 点击后是否及时反馈 | hang、交互延迟 |
| 动画 | 运动是否连续 | hitch、frame lifetime |
| 内存 | 是否峰值过高或泄漏 | footprint、allocation、jetsam |
| CPU | 是否做了过多计算 | CPU time、hot stack |
| 网络 | 是否快且可靠 | 成功率、p50/p95/p99、流量 |
| 能耗 | 是否耗电发热 | wakeup、timer、location、thermal |
| 稳定性 | 是否崩溃或被系统终止 | crash-free、watchdog、jetsam |
| 构建 | 团队是否高效 | clean/incremental build、缓存命中 |

## 3. 性能实验设计

必须固定或记录：

- 设备型号；
- OS 版本；
- Release/优化配置；
- App 版本和数据集；
- 冷/温/热状态；
- 网络条件；
- 电量和 thermal state；
- 样本数；
- 统计分布而非单一平均。

基线、变更和回归必须使用同一完成定义。

## 4. 启动诊断

分段：

```text
系统装载
→ pre-main
→ main / App 初始化
→ Scene/Window 建立
→ 首帧提交
→ 首屏数据完成
→ 用户可交互
```

检查：

- 动态库和符号装载；
- `+load`、静态初始化；
- 主线程磁盘/网络；
- 依赖容器构建；
- 首屏无关 SDK；
- 首屏 View 层级和布局；
- 数据解码、图片处理；
- “延后”是否造成随后卡顿。

验证不能只追求系统记录的 launch time，还要保住真实可用性。

## 5. 响应与动画

### Hang

主线程长时间不能处理事件。常见原因：

- 同步 I/O；
- 锁和 semaphore 等待；
- 大量计算；
- 错误的主队列 sync；
- 过多布局/状态更新；
- 低 QoS 工作阻塞高 QoS。

### Hitch

某一帧未在显示预算内完成。可能发生在：

- App commit 阶段；
- Render 阶段；
- GPU；
- 资源上传；
- 高频 SwiftUI body/layout。

工具：

- Hangs；
- Hitches；
- Time Profiler；
- SwiftUI 性能工具；
- signpost；
- Thread Performance Checker。

## 6. 内存

### 6.1 问题分类

- Leak：对象永久不可达但未释放或所有权环；
- Abandoned memory：仍被引用但业务不再需要；
- Peak：短时间大量临时对象；
- Fragmentation：可用空间碎片；
- Dirty memory：修改后需要物理驻留；
- VM / mapped file：映射资源；
- Cache 无上限；
- 大图解码和多份副本。

### 6.2 工具

| 工具 | 回答 |
| --- | --- |
| Memory Gauge / Report | 当前和峰值大概多高 |
| Memory Graph | 哪条强引用链保留对象 |
| Allocations | 哪些类型何时分配、是否增长 |
| Leaks | 部分泄漏模式 |
| VM Tracker | 虚拟内存区域和映射 |
| Zombies | 谁给已释放对象发消息 |
| ASan | 越界、use-after-free 等内存错误 |

Memory Graph 看到对象存活不等于泄漏；要先定义它此时是否应该释放。

### 6.3 修复顺序

1. 复现具体用户流程；
2. 标记期望释放点；
3. 查看引用图或 allocation stack；
4. 修复所有权/取消/缓存；
5. 重复流程多轮，观察基线是否回落；
6. 在真实设备看峰值和 jetsam 风险。

## 7. CPU 与算法

Time Profiler 关注：

- 主线程；
- self time 与 total time；
- 调用树；
- 重复小调用累积；
- 锁等待和系统调用；
- Release 优化后的符号。

优化路径：

- 消除不必要工作；
- 降低算法复杂度；
- 批量化；
- 缓存稳定结果；
- 增量更新；
- 将非 UI 工作移出主执行域；
- 并行化仅在任务可拆且收益大于调度成本时使用。

## 8. 崩溃与系统终止

### 8.1 崩溃类型

- Swift trap：数组越界、强制解包、precondition；
- Objective-C exception：unrecognized selector、KVC 等；
- signal：`EXC_BAD_ACCESS`、非法指令等；
- watchdog：启动、主线程、后台或扩展超时；
- jetsam：内存压力下系统终止；
- abort/assert；
- C/C++ 未定义行为。

### 8.2 调查

1. 确认版本、设备、OS、发生率和用户流程；
2. 符号化，匹配正确 dSYM；
3. 找 crashed/triggered thread；
4. 区分异常现场和真正根因；
5. 结合 breadcrumbs、业务状态和前序日志；
6. 用相同输入复现；
7. 修复并加回归；
8. 观察分版本发生率。

不能只看调用栈最顶一行。

## 9. Sanitizer 与运行时检查

| 工具 | 发现 | 限制 |
| --- | --- | --- |
| ASan | 越界、use-after-free 等 | 有明显运行开销，不负责泄漏 |
| TSan | 数据竞争 | iOS 设备支持受限，通常用模拟器；开销大 |
| UBSan | C 系语言未定义行为 | 不覆盖全部 Swift 问题 |
| Main Thread Checker | 违反主线程要求的系统 API | 不证明所有业务主线程安全 |
| Thread Performance Checker | 优先级反转、部分主线程重活 | 是提示，需要结合调用链 |

工具没报错不等于没有问题；测试覆盖决定能观察到哪些路径。

## 10. 测试体系

```text
静态检查 / 编译器
→ 纯函数与领域单元测试
→ 数据/网络/持久化集成测试
→ 模块/页面测试
→ UI 关键路径
→ 性能和稳定性测试
→ 灰度与线上观测
```

### 10.1 单元测试

- 测行为，不绑定私有实现；
- 注入 clock、UUID、network、store、scheduler；
- 覆盖正常、边界、失败、取消；
- 避免真实 sleep；
- 断言状态转换和副作用。

### 10.2 异步测试

- 使用 async XCTest API；
- 明确超时和取消；
- 不依赖任务完成顺序；
- 把不可控外部依赖替换为确定实现；
- 对 Actor reentrancy、过期结果和重复回调做专门测试。

### 10.3 UI 测试

适合：

- 核心用户路径；
- 跨模块集成；
- 可访问性标识；
- 启动和导航；
- 截图/视觉回归的关键页面。

不适合把所有业务分支都堆在慢而脆弱的 E2E 测试里。

### 10.4 性能测试

XCTest 可测时间、CPU、内存、storage、launch、hitch 等指标。需要：

- 稳定 fixture；
- 明确 baseline；
- 多次迭代；
- 允许合理噪声；
- 失败能定位到真实变更。

## 11. 可观测性

### 11.1 日志

- 使用结构化字段；
- 分级；
- correlation ID；
- 隐私标记与脱敏；
- 避免高频热路径大量字符串构建；
- 记录状态转换，不记录敏感 payload。

### 11.2 Signpost 与 Trace

用于连接：

```text
用户动作
→ 页面 action
→ 网络请求
→ 数据处理
→ 状态提交
→ 首帧/完成
```

只有开始/结束成对、ID 稳定、失败路径闭合，trace 才可信。

### 11.3 线上指标

- 分版本、设备、OS、网络、地区；
- 看分位数和长尾；
- 变更前后对照；
- 灰度 cohort；
- 防止采样偏差；
- 业务成功率与技术指标一起看。

## 13. 高频问题

### Q1：如何定位内存泄漏？

先定义预期释放点，再用 Memory Graph 看强引用链、Allocations 看增长和分配栈；修复后重复流程验证基线回落。

### Q2：平均 FPS 很高为何用户仍觉得卡？

平均值掩盖长尾 hitch/hang；需要看帧生命周期、交互延迟和具体卡顿事件。

### Q3：单元测试全部通过能否发布？

不能单独证明跨模块、真实设备、性能、安全和用户流程；需要按风险补充集成、UI、性能和灰度证据。

### Q4：偶现崩溃怎么查？

符号化、聚类版本/设备/路径，结合前序状态和日志，建立可重放输入；不要只靠猜测加 nil 判断。

### Q5：怎样证明优化没有“数字作弊”？

冻结用户可见完成定义、同环境对照、多样本分布，同时检查正确性与业务成功率。
