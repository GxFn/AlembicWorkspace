# 计算机科学基础：iOS 知识体系的根

> 知识树定位：A0.1 数据结构、A0.2 算法、A0.3 操作系统、A0.4 网络与分布式、A0.5 数据库、A0.6 编译链接。

## 1. 为什么 iOS 面试需要这一层

iOS 上层问题通常是基础问题的具体表现：

| iOS 现象 | 基础根因 |
| --- | --- |
| 列表查找慢 | 数据结构、算法复杂度、缓存局部性 |
| 主线程卡顿 | 调度、同步 I/O、锁、CPU 计算 |
| App 内存增长 | 虚拟内存、对象生命周期、缓存、映射文件 |
| 弱网重试重复下单 | 分布式部分失败、幂等、一致性 |
| 数据库查询慢 | 索引、查询计划、事务 |
| 启动慢/包大 | 编译、链接、动态库、符号和装载 |

面试不要求把 iOS 工程师变成算法研究员或内核工程师，但要能把问题定位到正确抽象层。

## 2. 数据结构

### 2.1 选择框架

选择数据结构时同时看：

- 操作：查询、插入、删除、遍历、最值；
- 复杂度：平均、最坏、摊销；
- 数据规模与分布；
- 内存布局和缓存局部性；
- 是否有序；
- 是否需要稳定顺序；
- 并发读写；
- 实现和维护成本。

### 2.2 基础结构

| 结构 | 优势 | 代价 | iOS 场景 |
| --- | --- | --- | --- |
| Array | 连续、随机访问、局部性好 | 中间插删 O(n) | 列表快照、批量模型 |
| Linked List | 已知节点位置插删方便 | 查找慢、节点额外内存、局部性差 | 特定队列/缓存内部结构 |
| Stack | LIFO | 只访问栈顶 | 导航、解析、DFS |
| Queue/Deque | FIFO/两端操作 | 随机访问弱 | 任务、消息、BFS |
| Hash Table | 平均快速查询 | hash、冲突、扩容、无天然顺序 | ID→模型、去重、缓存 |
| Set | 唯一性、成员判断 | 与 Hash 同类成本 | 已加载 ID、权限集合 |
| Heap | 快速取最值 | 任意查找不快 | 优先级任务、Top K |
| Tree | 层级、有序变体 | 平衡和实现成本 | UI/文件树、索引 |
| Trie | 前缀查询 | 内存可能较大 | 搜索建议、路由 |
| Graph | 关系和依赖 | 遍历/存储复杂 | 模块依赖、页面路由、任务图 |

### 2.3 Hash

需要理解：

- 相等对象必须有相同 hash；
- hash 相同不代表相等；
- 冲突需要桶/开放寻址等策略；
- load factor 过高会降低性能；
- 扩容可能产生瞬时成本；
- 作为 Dictionary/Set key 的字段在存储期间不应破坏 Hashable 不变量。

### 2.4 LRU Cache

经典 O(1) LRU：

```text
Hash Map：key → node
+
Doubly Linked List：按最近使用排序
```

访问：

- map O(1) 找节点；
- 移动到头部；
- 超预算时淘汰尾部。

真实图片缓存还要考虑按 cost 淘汰、内存 warning、线程安全和系统 `NSCache` 行为。

## 3. 复杂度与算法

### 3.1 复杂度

- O(1)：与输入规模无关的上界模型；
- O(log n)：二分、平衡树；
- O(n)：单遍扫描；
- O(n log n)：常见比较排序；
- O(n²)：双重成对比较；
- 指数级：组合爆炸。

复杂度不包含全部现实成本。移动端还要看：

- allocation；
- ARC retain/release；
- branch；
- cache locality；
- Unicode；
- I/O；
- 网络；
- 能耗。

### 3.2 高频模式

| 模式 | 识别信号 | 例子 |
| --- | --- | --- |
| Binary Search | 有序、单调边界 | 查第一个满足条件的位置 |
| Two Pointers | 有序/两端/配对 | 去重、区间 |
| Sliding Window | 连续区间、动态约束 | 最长无重复子串 |
| Prefix Sum | 多次区间求和 | 时间序列统计 |
| Hash Lookup | 需要从 O(n²) 降到 O(n) | Two Sum、去重 |
| DFS/BFS | 树/图遍历 | 页面路由、依赖扫描 |
| Topological Sort | 有向依赖顺序 | 模块/任务执行顺序 |
| Heap | 动态最值、Top K | 优先队列 |
| Backtracking | 枚举组合并剪枝 | 权限/配置组合 |
| Dynamic Programming | 重叠子问题、最优子结构 | 路径、编辑距离 |

### 3.3 解题流程

```text
复述输入/输出
→ 澄清规模与边界
→ 给暴力解
→ 找重复工作/单调性/结构
→ 写不变量
→ 选择数据结构
→ 证明正确
→ 分析时间和空间
→ 测空、单元素、重复、极值
```

不要先背模板再强套。

## 4. 操作系统

### 4.1 Process 与 Thread

- Process 是资源和地址空间隔离单位；
- Thread 是进程内执行流和调度单位；
- 同进程线程共享大部分地址空间和资源；
- 线程有独立栈、寄存器和调度状态；
- 上下文切换有成本；
- 创建过多阻塞线程会造成内存和调度压力。

Swift Task 和 Dispatch Queue 是更高层调度抽象，不等于固定线程。

### 4.2 User 与 Kernel

应用通常运行在用户态，通过 system call 请求内核执行：

- 文件 I/O；
- 网络；
- 线程/进程；
- 虚拟内存；
- 定时与事件等待。

同步 I/O 在主线程卡顿，本质是主执行流等待系统/设备完成工作。

### 4.3 Virtual Memory

概念：

- 每个进程看到虚拟地址空间；
- page 是映射和管理单位；
- page fault 可能触发映射、加载或复制；
- `mmap` 将文件/匿名内存映射到地址空间；
- dirty page 需要物理驻留或写回；
- copy-on-write 让共享页面写入前再复制。

iOS 内存面试不只看对象 retain。大图、映射文件、图形表面、缓存和脏页都影响 footprint。

### 4.4 同步问题

死锁经典必要条件：

1. 互斥；
2. 持有并等待；
3. 不可抢占；
4. 循环等待。

工程上用：

- 统一锁顺序；
- 缩短临界区；
- 不在锁内未知回调/I/O；
- 超时不是根治；
- 用不可变数据、单写者或 Actor 减少共享。

### 4.5 I/O

- buffered I/O 与缓存；
- 小块频繁读写 vs 批量；
- 顺序 vs 随机；
- fsync/持久性成本；
- 文件协调和原子替换；
- 主线程同步磁盘会影响响应；
- “异步”接口仍需理解内存峰值和取消。

## 5. 网络与分布式基础

### 5.1 连接主链

```text
URL
→ DNS
→ IP route
→ TCP 或 QUIC
→ TLS
→ HTTP
→ API
```

每层失败含义不同。客户端错误模型应保留足够分类用于体验、重试和指标。

### 5.2 TCP、UDP 与 QUIC

- TCP：可靠、有序字节流，有连接和拥塞控制；
- UDP：数据报，不提供可靠有序交付；
- QUIC：基于 UDP 在用户空间实现安全、多路复用等能力；
- HTTP/3 使用 QUIC；
- App 通常通过 URLSession 等高层 API 使用，不自行重造协议。

### 5.3 TLS

目标：

- 机密性；
- 完整性；
- 服务端身份验证；
- 可选客户端身份。

证书验证、域名、信任链和系统策略共同决定连接是否可信。加密连接不代表业务授权正确。

### 5.4 分布式系统现实

- 网络会超时；
- 超时不代表服务端没执行；
- 消息可能重复、延迟、乱序；
- 客户端时钟不可靠；
- 部分组件成功、部分失败；
- 重试会放大负载；
- “exactly once” 通常需要端到端幂等和状态设计。

客户端关键写操作使用操作 ID，让服务端识别重复。

## 6. 数据库

### 6.1 Relational Model

- table/row/column；
- primary key；
- foreign key；
- normalization 与必要反规范化；
- query 和 join；
- index。

### 6.2 Index

索引以额外空间和写成本换查询性能。判断：

- 查询条件和排序；
- 选择性；
- 组合索引顺序；
- 是否覆盖查询；
- 写入频率；
- query plan。

“加索引”不是无成本答案。

### 6.3 Transaction 与 ACID

- Atomicity：事务全成或全不成；
- Consistency：维护业务/数据库不变量；
- Isolation：并发事务之间的可见性；
- Durability：提交后按合同持久。

移动端本地写入常把“业务对象变更”和“待同步 operation”放同一事务，避免 UI 已变化但同步记录丢失。

### 6.4 Isolation

需要认识：

- dirty read；
- non-repeatable read；
- phantom；
- lost update。

具体数据库和框架的隔离实现需查文档。业务层仍可能需要版本号或 compare-and-set。

## 7. 编译与链接

### 7.1 主流程

```text
源代码
→ 预处理（C/OC）
→ 编译为中间/机器表示
→ 汇编为 object file
→ 链接符号与依赖
→ Mach-O / Library / Framework
→ 签名
→ 装载执行
```

### 7.2 Static 与 Dynamic

| 维度 | Static | Dynamic |
| --- | --- | --- |
| 代码进入 | 链接进最终产物 | 运行装载依赖 |
| 启动 | 少一个动态装载边界，但仍看整体 | 动态库过多可能增加装载工作 |
| 共享/分发 | 代码可能复制到多个产物 | 可形成独立二进制模块 |
| 符号/资源 | 由最终链接整合 | 有独立 bundle/加载语义 |

实际结果受链接器、App Store 处理、系统缓存和产物结构影响，需要测量。

### 7.3 API、ABI 与 Module Stability

- API compatibility：源代码调用合同；
- ABI compatibility：已编译二进制交互合同；
- Module stability：编译器可读取稳定模块接口；
- library evolution：库升级保持二进制兼容的设计。

内部 App 模块与对外二进制 SDK 的权衡不同。

### 7.4 Debug 与 Release

- 优化级别改变内联、去虚化、调试体验；
- Debug 性能不能代表用户版本；
- Release 崩溃需要 dSYM 符号化；
- 条件编译不能造成关键行为未经测试；
- 性能基准使用接近发布的配置。

## 8. 高频问题

### Q1：为什么 Array 中间插入是 O(n)？

连续布局需要移动后续元素；还可能涉及扩容和元素生命周期操作。

### Q2：Dictionary 为什么只是平均 O(1)？

Hash 计算、冲突、负载因子和恶意/极端分布会影响；扩容有摊销成本。

### Q3：内存占用为什么不等于 Swift 对象大小总和？

还有 allocator、对齐、图形资源、映射文件、虚拟内存区域、缓存和脏页。

### Q4：请求超时后能否直接重试下单？

超时不证明服务端未执行；需要幂等操作 ID 和服务端状态查询/去重合同。

### Q5：数据库事务能否解决所有同步冲突？

事务只覆盖特定数据库边界；跨设备、跨服务和离线同步仍需版本、幂等与冲突策略。

### Q6：模块越多构建越快吗？

不一定。依赖图、链接方式、代码生成、缓存、变更范围和工具链共同决定，需要构建时间证据。
