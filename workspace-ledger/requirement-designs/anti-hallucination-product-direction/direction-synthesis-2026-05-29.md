# Alembic 反幻觉产品方向纪要

执行日：2026-05-29
类型：需求设计 / 方向纪要（纯方向与方法论，不含验证任务派发）
状态：方向已形成，进入"先造、后调优、渐近无人"阶段

> 本文件汇总一次跨多轮的方向讨论，目的是为后续动手提供方向锚点。
> 它记录的是**判断与方法论**，不是已验证的代码事实，也不是可派发的执行计划。
> 文中涉及的代码链路事实，单列在第 9 节并标注证据来源；其余为方向推断。

## 1. 一句话定位

**Alembic 与 codex-control-workspace 是同一个使命在两个尺度上的实现：在没有人盯着的时候，用代码事实拒绝幻觉。**

- 单项目尺度：Alembic —— 用确定性代码证据约束 Agent 对单个项目的理解与知识沉淀。
- 多仓库尺度：codex-control-workspace —— 用确定性验收门禁约束多仓库协作与无人值守自动化。

两者解决的是同一类根本问题：**有限的上下文空间 vs 庞大的代码现实**，并在这个约束下**拒绝幻觉**。

---

## 2. 核心命题：拒绝幻觉

整个产品的所有功能，都可以归约为"拒绝某一类幻觉"：

| 功能 | 拒绝的幻觉类型 |
| --- | --- |
| Recipe 装"判断"而非"事实" | 把通用知识误当项目特写 |
| sourceRef 确定性校验 | 模型声称的引用根本不存在 |
| 证据贯穿闭环（而非事后筛） | 自由生成、查无此据的内容 |
| PCVM golden set + 北极星 | 指标好看但判断退化（含人自己的幻觉） |
| control-workspace 验收门禁 | 子仓库"说做完了、其实没做" |
| VAD 停止卡 + 确定性 finish | 夜里无人时，错误被包装成成功继续狂奔 |

**六件看似不同的事，是同一件事。** 这是一个有灵魂的产品定位——所有功能指向一个命题。

---

## 3. 知识库要不要做：取决于它装什么

结论：**知识库方向值得做，但当前体量可能偏大；真正该死守的是 live 检索/AST 永远做不到的那部分。**

- 不该押"存储代码事实"——那是 AST/live 工具的主场，存了只是保鲜负担。
- 该押"经验性判断"——为什么这么设计、坑在哪、改的时候要注意什么。
- 判断曲线：装"判断"越多越无可替代；装"事实"越多越像在和 grep 做无谓竞争。

---

## 4. Recipe 定位：从"项目特写"再深一刀

- 用户最初定位"Recipe = 项目特写"——**抓对了专属性轴，漏了判断 vs 事实轴**，是 70 分定位。
- 升级定位：**Recipe = 这个项目的"判断与经验"，不是这个项目的"事实"。**
  - 口语版：**Recipe 装的是"为什么"和"小心什么"，不是"是什么"。**
- 两刀都要切：
  1. 专属性（原定位已覆盖）→ 挡掉通用知识。
  2. 判断性（原定位缺的）→ 挡掉 AST 当场能算、注定过期的事实。
- "项目特写陷阱"：像 `VideoPlayViewModel 调用了 AOXPlayer`——是项目专属，但是确定性事实，会过期，不该进 Recipe。

---

## 5. 三类知识，各归各位

```
确定性代码事实（调用图/import/签名） → 工程引擎算，实时跟随，不用 LLM
工作流/契约/意图（该怎么做、边界）   → 人写 AGENTS.md / Constitution
经验性判断（为什么/坑/怎么改）       → Recipe 的唯一主场（LLM 生成初稿 + 确认背书）
```

**原则：能工程算出来的，就别用 LLM 算。** LLM 的职责被压缩到唯一不可替代的格子：把"不能被计算"的判断生成成初稿，再由确认机制背书。

---

## 6. 护城河的三条腿（互相加固）

1. **商业模式缝隙（对手不会做）**：CC / Codex 是按 token、会话级计费的产品，结构性地**没有动力**做"一次算、永久共享、可迁移、宿主无关"的节约——那等于让它们革自己的命。
2. **算力稀缺（省下的在升值）**：Agentic 编程吃的是前沿推理这一档，它**没有变便宜**，在缺卡背景下涨价/限流/变相涨。"一次算、永久复用"省下的，是一种稀缺性正在上升的资源；缺卡让对手更没动力做这种节约。
3. **判断层深度（够用版够不着）**：对手可能推一个"够用的轻量 repo memory"做到 70 分免费送。要赢的不是它们的全力，是它们的"顺手够用版"——而判断层（为什么、坑在哪）需要"确认"这个慢动作，是它们"快、即时、会话级"的产品哲学最难做的。

**三条腿同向叠加：商业缝隙 × 算力稀缺 × 判断深度。**

> 守门提醒：别把护城河押成"纯省钱"（会被 token 降价掏空），要押成"省的是稀缺前沿推理 + 结果可共享可累积可迁移"。价值的承重墙是"质量压倒 + 可共享"，缺卡只是放大器。两者是乘法。

---

## 7. 最强模型悖论

- **投资决策对**：扫描是一次性、可沉淀的动作，舍得用最贵的最强模型，单次贵无所谓——对手不会跟。
- **逻辑推断错**："最强模型 ⇒ 结果不会更差"不成立。结果质量是乘积链：

  结果质量 = f(模型能力, 输入完整性, 问对问题, 可校验, 可保鲜)

  最强模型只拉满第一项，其余每项都能独立把结果拖差。
- **最危险的反直觉点**：**最强模型让错误更难被发现**。弱模型错得"像错的"，会被过滤；最强模型错得"像对的"——流畅、自信、自洽，一旦被确认机制盖章、跨会话复用，就是一个高可信度的错误被放大无数倍。
- **推论**：在"确认后永久复用"的架构里，确认 + 校验 + sourceRef 绑定 + 保鲜不是辅助功能，是用来接住"最强模型也会犯、且更难发现的错"的**安全网**。模型越强，这层越不能省。

## 8. 慢的两种类型

- **慢法 A（护城河）**：慢在"校验"——拿确定性事实去证伪模型的判断。每一秒都在降低高可信幻觉混进库的概率。CC 结构上不会做。
- **慢法 B（浪费）**：慢在"反复生成"——让 LLM 一遍遍重答、自我反思，但没有外部确定性真值证伪。多嚼几遍不会把幻觉嚼成真相，只会让它更自洽、更危险。

判据（问每个"反复"的环节）：**这一轮的输出，有没有可能被一个"代码里查得到的事实"直接驳回？** 能 → A，值得；不能、只是"让模型再想想" → B，该砍。

**不要拿 CC 的速度当标杆。** 正确对照不是"Alembic 冷启动 vs CC 一次回答"（必输也该输），而是"CC 第 1 次问 vs Alembic 沉淀后第 N 次问"。价值在第 N 次复用才兑现。

## 9. 冷启动链路代码事实（已验证）

> 证据来源：只读探索 `AlembicAgent/src` 与 `Alembic/lib`，2026-05-29。
> 结论：**代码证据（sourceRef / AST / 调用图）是冷启动闭环的主导，而非多轮 LLM 自洽。**

确定性证伪关卡（带牙齿、驳回不触发"再想想"）：

| 关卡 | 文件 / 函数 | 用什么事实驳回 LLM |
| --- | --- | --- |
| N11 sourceRef 有效性 | `Alembic/lib/.../BootstrapPcvNodeLocalEvidence.ts` `validateSourceRef()` | LLM 声称的源引用在真实文件索引 `fileSet` 中查不到 → `file-not-found` 驳回 |
| accepted/success 一致性 | 同上 `buildPcvN11ProduceEvidence()` | LLM 说提交 N 个、工具实际成功 M 个，N≠M → `blocked` |
| Producer 阶段存在性 | 同上（N8 stage policy） | profile 配置事实，LLM 改不动 |
| N12 持久化可发现性 | 同上 `buildPcvN12ConsumerPersistenceEvidence()` | LLM 说"提交了标题 X"，SessionStore 查不到 → `blocked` |

关键性质：`rejection_gate` 的 `toolCallCount: 0`、失败立即记 rejected、无自动 fallback/degrade —— 代码事实驳回时，系统不让 LLM 用花言巧语把自己捞回来。

**当前形态的待优化点**：确定性校验是"事后筛除"（LLM 先自由生成 analyze ~16 轮 / produce ~12 轮，校验在之后介入）。
- 库是干净的（筛子真的硬）。
- 但中间的生成迭代里，可能混有"由自我反思驱动"（B）而非"由取证驱动"（A）的轮次，存在空转 + 被驳回候选白烧稀缺算力的代价。

## 10. 证据贯穿（下一步方向，非当前任务）

- 不是"换主线"，证据一直是主线；是让它从"终点一道关"贯穿成"全程一个场"。
- 不是"增强每一轮的反思"（那是给高可信幻觉踩油门），是**把每一轮的燃料从"模型自评"换成"代码取证"**：动笔前先查证据，让证据（而非模型偏好）决定这一轮结论和下一轮方向。
- **让代码矫正 LLM，不要让 LLM 矫正 LLM。**
- 守门边界（"更彻底"不等于"处处要证据才能说话"）：
  - **事实型断言**：证据是裁判，查不到就驳回。
  - **判断型结论**：证据是地基（可追溯到哪些代码事实），**不能因"查无此据"驳回**——判断本就不在代码里。
- 一句话：**事实必须被证据裁判，判断必须被证据锚定，但判断不能被证据驳回。** 守住这条，贯穿是加固；越过这条，会把最值钱的判断层误杀成 AST 复读机。

## 11. 与 Claude Code 的分水岭

- CC **有**证据（grep、读文件、跑测试），但是"足够证据"（satisfice，够答这次就停），不是"彻底证据"（maximize，覆盖到可证伪可沉淀）。
- CC 结构上不会"彻底"：卖即时性、不沉淀、缺卡、且把"证据够不够"的裁判权交给模型自己。
- **真正的分水岭不是"证据多少"，是"谁来判定证据够不够"**：CC 是模型自判（会被高可信幻觉骗），Alembic 是确定性关卡仲裁（非模型、可证伪）。
- 守门提醒：别把"彻底"当目标，把"可证伪"当目标。一查就到的局部事实问题上，彻底 = 慢版 CC；只有在"足够不够"的系统性/判断性问题上，可证伪的证据才兑现护城河。

## 12. PCVM 方法论与最佳实践

本质：PCVM 就是"评估驱动的 LLM 系统开发（eval-driven development）"在 Alembic 上的实例化。

### 12.1 四个必须先想清的坑

1. **Goodhart（指标即目标就不再是好指标）**：指标好看 ≠ 事情做对。`sourceRefValidity` 打到 0 可能是"真变好"，也可能是"系统/人学会只产容易过校验的安全结论，把判断层饿死"。
2. **小阶段达标 ≠ 链路达标**：每段代理指标全绿，全局产出仍可能没用或误导。
3. **指标锁死"事后筛除"形态**：只测终点结果指标，会主动阻止"证据前移"（因为前移短期让事后指标波动）。
4. **调优循环太贵太慢**：冷启动烧时间和稀缺算力，必须跑在可重放的最小链路上。

### 12.2 用户的关键澄清及其含义

- PCVM 是链路**之外**的观测/拆解层，**LLM 不知道指标**，调整者是人（改 prompt + 工具包）。
- 含义：**机器版 Goodhart 不成立**（系统不会自动刷分）。**但 Goodhart 搬到了"人"身上**——会被指标带偏的不再是模型，是优化者本人。
- 人肉调优三软肋：
  1. **错误归因**：LLM 随机性可能比改动效果还大，把"运气"当"有效"。
  2. **过拟合单项目**：只在 BiliDili 调，换项目可能更差。
  3. **prompt 牵一发动全身**：为提 N11 改 produce 提示词，可能无声拉低 analyze 判断质量。

### 12.3 成熟最佳实践（按优先级）

1. **建 golden set（含判断型样例）+ holdout**：人确认的标准答案是唯一能对抗高可信幻觉的锚。holdout 绝不用于调 prompt，只用于最终验收，防过拟合。分层抽样：必须同时含"事实型"和"判断型"样例，否则判断层因不在评估集而被饿死。
2. **三层指标**：
   - 北极星（1 个）：判断是否真实、被采纳、可用 —— 防全局失败 + 防只盯局部把判断层调没。
   - 过程指标：证据是否在生成时在场（取证驱动占比）—— 让"证据前移"可被测量。
   - 结果指标：sourceRefValidity / accepted / persistence —— 已有，做得好。
3. **把"调一眼"升级成"受控实验"**：同输入跑 N≥5 次取分布不取单值；单变量原则；改动留痕 + 配对 A/B；每次跑全套 golden set 做回归。
4. **LLM-as-judge 套确定性枷锁**：只评"难确定性度量"的（判断有用性/清晰度），绝不评能确定性算的（sourceRef）；先用 golden set 校准 judge；judge 分只作参考排序，门禁永远是确定性关卡。
5. **一次攻一个瓶颈节点**：先测找最大瓶颈 → 只调那个 → 回归全链路确认无副作用 → 锁定再攻下一个。

### 12.4 最小可行版（别一上来全套）

**20-30 条小 golden set（一半事实、一半判断）+ 一个北极星 + replay 多次取分布。** 这三样就能让优化者 80% 不被自己骗。其余等撞到对应问题再加。

## 13. codex-control-workspace 定位与判断

### 13.1 必要性（已确认，无保留）

四个职能全部成立：
1. 统一把需求发布给各子仓库执行。
2. 统一验收、测试、归档（否则推进无法收口）。
3. **子仓库上下文分区**：单窗口扛不住多仓库全貌，总控持有全局、按需切片分派——这是 Alembic"上下文工程"哲学在多仓库尺度的人工版。
4. **VAD 无人值守**：夜间独立执行，醒来收结果。

### 13.2 VAD 的本质与最高风险

- **无人值守 = 移除"人在场拦截高可信幻觉"这道防线。**
- 因此 VAD 的安全性**100% 押在确定性验收门禁上**——夜里唯一醒着的裁判必须是代码事实，绝不能是 agent 自评。
- AGENTS.md 里大量"停止卡 / finish JSON 必须返回 X 才能继续 / thread id 必须真实"——本质是保证"夜里出错时安全停下，而不是带错狂奔"。设计直觉对。

### 13.3 保留的质疑（优化问题，非存废）

- 规则通胀风险：每次翻车都加一条 AGENTS.md 规则，可能进入"规则越多 → 越难遵守 → 越易违反 → 再加规则"。
- 可下沉性：能被脚本强制校验的错，不必再用文字规则提醒（文字规则 agent 可能不遵守，脚本校验是强制的）。
- 配置漂移：`workspace.config.json` 用 generic 占位名（`BaseWindow` 等、指向不存在的 `../BaseWindow`），与真实运转用的仓库名（`Alembic` 等）对不上而系统照常跑——说明真值散在文档（人读）而非结构化配置（机器校验）。无人值守场景下尤其危险。

### 13.4 三个自检问题

1. 若停止维护 VAD、改回手动复制提示词，会损失多少？损失不大则 VAD 偏过度工程。
2. AGENTS.md 最近新增的规则，有几条真的阻止了重复翻车，有几条只是"写了感觉安心"？
3. 这套总控经验，留在脚手架，还是反哺进 Alembic 产品？定了投入策略才能定。

## 14. 元层风险（最该长期记住的一条）

**"拒绝幻觉"的系统，最大风险是误以为自己已经拒绝了幻觉。**

- 现有防线擅长拒绝**第一类幻觉：无中生有**（查无此据、没做谎称做了）——这层做得好。
- 真正的终极对手是**第二类幻觉：有据但错**——引用真实存在的代码，却对它做出错误判断；跑完真实流程，却在错误方向上跑得很完整；每个局部都 grounded，合起来的结论却错。
- 现有确定性校验**结构上接不住第二类**——它们校验"有没有据"，而第二类的特征是"据是真的，推论是错的"。
- **唯一能从"校验完整性"升级到"校验正确性"的零件，是 golden set（人确认的真值）。** sourceRef / finish JSON / 验收门禁都只能回答"全不全"，只有人确认的真值能回答"对不对"。

## 15. 节奏共识与书签

- **方向**：自洽、有护城河、与行业商业模式缝隙同向。已可支撑动手。
- **节奏**：先造 → 后调优 → 渐近无人。目标是"朝无人方向走、保留人的关键节点"，是渐近线不是奇点。这个分寸成熟。
- **golden set 的正确时机**：不是现在（方向设计阶段不需要），是**第一次认真调 prompt、需要分辨"改动有效 vs 运气好"那一刻**才需要的仪器。

**书签（日后调优时再想起即可，非当前任务）：**
> 当开始相信"我的系统拒绝了幻觉"时，回来问一句：我拒绝的是"没有证据"，还是"错误的判断"？
> 前者已有仪器；后者要靠 golden set / 人确认真值，等需要时再造。
