# AlembicTest Exchange Policy

状态：长期规则
维护窗口：AlembicWorkspace
适用范围：总控窗口与 `AlembicTest` / `AlembicTest-IDE` 测试验证窗口之间的测试任务、测试结果和证据交流

## 两个测试职责窗口

总控必须先按测试对象选择职责窗口：

- `AlembicTest-IDE`：Codex Plugin、Codex host MCP、Codex 会话 / 本地环境、installed / packaged Plugin runtime smoke、direct-thread / IDE 投递读回等测试。它不承接 BiliDili / AlembicWorkspace 的 AI cold-start / rescan。
- `AlembicTest`：BiliDili、AlembicWorkspace 或其它受保护真实项目的 cold-start / rescan / after-run、AI/provider、Dashboard 手动观察、运行时监控和真实项目回归。它不承接 Codex Plugin / host 环境 smoke。

两个窗口可以共用 `AlembicTest` 仓库内的脚本、报告目录和说明，但执行前必须以当前计划 / dispatch packet / 测试单里的 `执行窗口` 为准；窗口名与测试对象不匹配时，停止并回报总控改派。

## 总控职责调整

总控窗口负责：

- 判断是否需要测试、测试目标是什么、为什么现在测试。
- 在任何测试启动前完成测试前边界与多条件判断，明确测试回答的问题、测试对象边界、自测范围、真实场景依赖、成功 / 失败可推出的结论、不能推出的结论和不应启动条件。
- 默认自行执行不依赖真实场景的验证：workspace 脚本测试、文档校验、状态机验证、targeted unit / probe、轻量集成验证、可构造的最小复现和可直接读取证据的验收复核。
- 明确测试输入、触发入口、观察点、完成标准、风险和禁止事项。
- 只有当测试需要真实项目、cold-start / rescan、Dashboard 手动观察、运行时监控、真实项目复现 / 回归或跨仓库集成环境证据时，才在专门测试交流文档中创建或更新测试单，并派发给 `AlembicTest`。
- 当测试对象是 Codex Plugin、Codex host MCP、Codex 会话 / 本地环境或 direct-thread / IDE 投递读回时，派发给 `AlembicTest-IDE`，不得占用 `AlembicTest`。
- 验收 `AlembicTest` / `AlembicTest-IDE` 回填的结果、证据、风险和下一步建议；验收前必须先判断总控能否直接补做最小复核。
- 根据测试结论调整总控计划、TODO、后续分派或返工任务。

总控窗口不得：

- 把 `AlembicTest` 当作默认测试窗口或默认确认队列。
- 把脚本测试、文档校验、状态机验证、targeted unit / probe、轻量集成验证或可构造最小验证推给 `AlembicTest`。
- 在已经看见代码 / 文档 / 脚本 / 自动化状态机缺口时，先派 Test 验证同一个已知缺口；应由总控或归属源码仓库先修正并验证。

总控窗口必须额外负责回填信任边界：

- 测试职责窗口的结论是测试窗口观察和建议，不是总控最终事实。
- 总控必须把测试职责窗口的自然语言结论、原始测试证据、总控独立裁决分开记录。
- 总控没有独立读取报告、命令输出、runtime JSON、日志摘要、截图、git 状态或其它原始证据前，不得把测试回填写成当前计划结论。
- 如果测试职责窗口只按文档做了简单操作，或回填信息与总控已知事实冲突，总控应标为 `待补证` / `待裁决` / `阻塞`，先复核测试单设计或源码事实，不得直接改文档后重新派发同一循环。

总控窗口不负责：

- 直接操作真实测试项目业务源码、UI、登录、网络、播放或用户数据。
- 亲自执行需要真实项目环境的 cold-start / rescan、Dashboard 手动观察、运行时监控、真实项目 smoke、复现或回归；这些动作必须通过 `AlembicTest` 测试单执行。
- 在总控窗口内保存真实项目复现脚本、真实场景测试配置或长期测试报告。

## AlembicTest / AlembicTest-IDE 职责

两个测试职责窗口共同负责：

- 读取总控测试交流文档中的测试单。
- 使用 `AlembicTest` 仓库内脚本、配置和文档执行测试。
- 按测试单限制执行，不扩大范围、不修改真实项目业务代码。
- 回填测试结果、证据、日志摘要、失败分类和下一步建议。
- 如果发现产品问题，指出归属仓库和最小复现路径，不在测试仓库内修产品实现。
- 明确区分“原始观察”和“测试窗口建议”：原始观察包括命令、输出、日志、runtime JSON、截图、报告路径、git 状态；建议可以包含归因猜测，但必须标注为建议，不得替代总控裁决。

`AlembicTest-IDE` 只做 Codex 插件和本地环境相关测试；`AlembicTest` 只做真实项目、AI、cold-start / rescan 和运行时监控相关测试。

## 专门测试交流文档

统一测试交流文档是：

```text
docs/workspace/current/test-exchange.md
```

这个文档用于：

- 总控创建测试单。
- 标记测试任务状态。
- 给出统一可复制提示词。
- 接收 `AlembicTest` / `AlembicTest-IDE` 的结果回填摘要。
- 链接 `AlembicTest/docs/` 中的详细测试报告。

注意：

- `AlembicTest` 仓库是独立测试仓库，不进入 AlembicWorkspace git 跟踪；`AlembicTest-IDE` 是同一仓库上的独立 Codex 职责窗口。
- `AlembicTest` / `AlembicTest-IDE` 可以按测试单回填 workspace 测试交流文档，但不得提交 AlembicWorkspace 仓库。
- 详细测试报告、脚本配置和测试资产应保存在 `AlembicTest` 仓库内；workspace 交流文档只保留总控需要验收和派发的摘要。
- `AlembicTest` 自身新增或修改的 probe、报告、脚本索引和临时测试资产不要求每轮提交；只要回填证据足够、产品仓库和真实测试项目没有非预期改动，总控不得把 `AlembicTest` 未提交测试资产当作验收阻塞。提交 hash 可以记录为 `无`。

## 测试流程

0. 总控先判断测试节奏：能自己验证的，先自己验证；只有依赖真实场景或 Codex 插件 / 环境职责窗口时才进入测试职责窗口。
1. 如果需要测试职责窗口，总控必须在当前计划或测试单中写清测试前边界与多条件判断：测试要回答的问题；测试对象 / 目标窗口 / 线程 / 项目边界；总控可自测项；必须交给对应窗口的真实场景或 Codex 插件 / 环境条件；成功能推出的结论；失败能推出的结论；不能推出的结论；停止或不开始条件。
2. 总控在 `docs/workspace/current/test-exchange.md` 新建或更新测试单。
3. 总控把测试单状态设为 `待启动`，并在当前总控计划 / index 中把正确职责窗口改为可发送。
4. 用户把统一提示词发送给 `AlembicTest` 或 `AlembicTest-IDE` 窗口。
5. 测试职责窗口按测试单执行，详细记录写入 `AlembicTest/docs/` 或当前测试单指定的报告目录。
6. 测试职责窗口在交流文档中回填摘要、原始证据、报告路径和下一步建议。
7. 总控先执行回填信任边界检查，确认哪些是原始证据、哪些只是窗口判断；证据不足时先判断总控能否直接补做最小复核，不能时才要求补测。
8. 总控验收回填，决定：
   - 测试通过，推进下一阶段。
   - 测试失败，分派给对应产品仓库修复。
   - 证据不足，要求对应测试职责窗口补测。
   - 测试风险不适合继续，暂停并等待用户确认。

## 状态

测试单状态只使用：

- `待确认`：测试目标或数据策略还需要用户确认。
- `待启动`：测试单已经可执行，可以发送给对应测试职责窗口。
- `执行中`：测试职责窗口正在执行。
- `待验收`：测试职责窗口已回填，等待总控验收。
- `已完成`：总控验收通过。
- `阻塞`：缺权限、缺上游、缺配置或等待用户决策。
- `暂停`：用户或总控明确暂停。

## 最小回填标准

每个测试单至少回填：

- 测试结论：通过 / 失败 / 取消 / 阻塞 / 未执行。
- 结论性质：原始观察 / 测试窗口建议 / 需要总控裁决。
- 对测试前边界判断的回填：实际执行是否命中预设对象 / 线程 / 项目 / 场景边界；若偏离，必须写明偏离，不能直接给通过 / 失败结论。
- 触发入口和执行范围。
- 使用配置或关键参数。
- job id / session id / Dashboard URL 摘要。
- 状态变化：active / completed / failed / cancelled / timeout。
- 候选数量或关键产物数量。
- 关键日志信号。
- 真实项目是否保持干净。
- 详细报告路径。
- 建议下一步和归属窗口。

总控验收时至少记录：

- 已独立复核的原始证据。
- 不采信或暂不采信的窗口判断及理由。
- 最终裁决状态：通过 / 失败 / 待补证 / 待裁决 / 阻塞。
- 下一轮派发是否允许启动；若允许，必须说明归因层级和避免重复循环的依据。
